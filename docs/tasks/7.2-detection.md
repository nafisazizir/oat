# 7.2 — Meeting detection (mic-in-use by meeting apps)
status: done
milestone: M7 · deps: 7.1 · branch: task/7.2-detection

## Goal
Notice when a call starts and offer "Start notes?", per D-21: a known meeting app holding mic input (Core Audio
process objects, ~1 Hz) combined with calendar overlap, with rules as pure, fixture-tested functions.

## Context
D-21 (rules, deliberate difference: browsers prompt only with calendar overlap), `research/granola/detection.md`
(reference), `native/oat-audio` (CLI structure, calendar subcommands from 7.1), `@oat/core` calendar helpers
(`currentMeetingFor`), `@oat/calendar`.

## Scope
In:
- Sidecar `mic-apps watch` (and `mic-apps list`): enumerate Core Audio process objects
  (kAudioHardwarePropertyProcessObjectList, kAudioProcessPropertyIsRunningInput, PID, bundle id) every ~1 s,
  emit JSON lines only on change; `--fixture <file>` replays a scripted timeline. Reading process objects does
  not prompt (verify in docs; if uncertain, only run with `--fixture` in tests). Swift tests with injected
  provider.
- `packages/detection` (`@oat/detection`): data — allowlist of meeting apps (Zoom, Teams, Slack huddles,
  FaceTime, Webex, Discord, Around, Tuple…; browsers Chrome/Arc/Safari/Edge/Firefox/Brave as `browser`),
  helper→parent bundle map; pure reducer `detect(state, input, now)` → actions (`prompt`, `dismiss`,
  `meetingEnded`) implementing: asymmetric debounce (appear immediately, gone after ~2 s), ~2 s prompt delay,
  2-min rate limit, no prompt while recording, per-app silence list, browsers only with calendar overlap,
  calendar event naming the meeting. `MicAppsSource` (sidecar | fixture).
- Fixture timelines (`fixtures/detection/*.json`) + exhaustive tests for every rule.
Out: desktop notification UI + wiring (done in 2.5/3.4 follow-up or 7.3), auto-stop (7.5).
Never run `mic-apps watch` without `--fixture` unless you've confirmed it can't prompt (document evidence).

## Acceptance criteria
- [x] Rules covered by fixture tests; sidecar fixture mode exercised from a Node int test.
- [x] `pnpm run ci` green.

## Design notes
(implementer, 2026-11-14)

**Split.** The sidecar only reports *processes running audio input* (unfiltered); every decision (allowlist,
helper mapping, debounce, prompts) is TypeScript in `@oat/detection`, so rules are pure and fixture-tested and
the allowlist can change without a Swift rebuild.

**Sidecar `oat-audio mic-apps`** (`native/oat-audio/Sources/OatAudioCore/MicApps/`, PROTOCOL.md → *Mic apps*):
- `list [--fixture f]` → one `{"type":"apps","apps":[…]}` line; `watch [--interval-ms n=1000] [--fixture f]` →
  `{"type":"ready",source,intervalMs}`, then an `apps` line on the first poll and on every change (full sorted,
  de-duplicated list, not a diff). Poll errors → one `{"type":"error","code":"poll_failed"}` per failure run.
  Stops on stdin EOF / `{"cmd":"stop"}` / SIGINT / SIGTERM (same as `calendar watch`). Protocol number unchanged.
- Entry `{pid, bundleId, appBundleId}`. `appBundleId` = outermost `.app` around the executable
  (`proc_pidpath` → path → `Bundle(path:)`), so nested helper apps (Chrome/Edge/Brave/Slack/Discord helpers)
  name their parent even without a map entry. No private API (no "responsible pid" dlsym).
- `MicAppsProvider` protocol: `CoreAudioMicAppsProvider` (process-object list → IsRunningInput, PID, BundleID)
  and `FixtureMicAppsProvider` (replays `steps[].micApps` of a detection timeline by elapsed time; injectable
  clock). `MicAppsDiffer` / `MicAppsRunner.Poller` are the testable loop; `main.swift` only wires a
  `DispatchSourceTimer`, stdout, signals, stdin.
- **TCC evidence:** the SDK header (`CoreAudio/AudioHardware.h`) documents these properties as process-object
  metadata and says nothing about permissions; Apple does not document either way. Not "documented evidence
  of no prompt", so per the brief **the real Core Audio path was never run** — only `--fixture` (CLI smoke,
  Node int test) and injected providers (Swift tests). First real run is a human checkpoint (README → *Mic
  apps*), which should also confirm the helper bundle ids seen in real calls.

**`@oat/detection`** (`packages/detection/src/`):
- `apps.ts` — `MEETING_APPS` (id, name, `native|browser`, noun call/meeting/huddle, bundle ids): Zoom, Teams,
  Slack, FaceTime, Webex, Discord, Around, Tuple, WhatsApp, Skype, Signal, Telegram, Gather, the Meet PWA;
  browsers Chrome, Arc, Dia, Safari, Edge, Firefox, Brave, Vivaldi, Opera, Chromium. `HELPER_PARENTS`
  (WebKit GPU/WebContent → Safari, `avconferenced` → FaceTime, Firefox plugin-container) and
  `HELPER_PREFIXES` (`us.zoom.*` → Zoom). Resolution: exact id → helper map → longest `<main id>.` prefix
  (`com.microsoft.teams2.modulehost`, `com.google.Chrome.helper`; a listed PWA id beats its browser) → vendor
  prefix → same chain on `appBundleId`. Long-tail bundle ids are unverified (checkpoint).
- `detect.ts` — `detect(state, input, now) → {state, actions}`, pure (tested: input state never mutated; time
  never goes backwards). Inputs: `micApps`, `recording`, `calendar`, `silenced`, `promptClosed`, `tick`.
  `nextDeadline(state)` says when to `tick`. Rules (config `DEFAULT_DETECTION_CONFIG`):
  1. processes → allowlisted apps, folded per app into a *presence* (pid/bundle kept current);
  2. asymmetric debounce: present at once, gone after 2 s absent; returning sooner continues the presence;
  3. one prompt decision per presence, 2 s after it appeared, only while the app currently holds the mic;
  4. gates in order (failing drops the candidate for that presence): not recording, app not silenced, no
     prompt on screen, none in the last 2 min (global), event not already prompted (one prompt per event);
  5. `currentMeetingFor` (7.1, D-21 window) names the meeting; **browsers prompt only with an event** —
     without one the candidate *waits* while the browser holds the mic and is re-checked on calendar changes
     and when an event's −90 s window opens (`nextDeadline` schedules that);
  6. `dismiss` reasons: `app_gone`, `recording`, `silenced`, `timeout` (2 min unanswered); `promptClosed`
     (user acted) clears without an action;
  7. `meetingEnded` when the last meeting app is debounced away: `startedAt`, `endedAt` (= real mic release,
     before debounce), `appIds`, `recording`, `eventId` (named by a prompt) — the input 7.5 auto-stop needs.
  Additions beyond D-21's list, all small and test-pinned: one prompt per calendar event, prompt timeout,
  native-before-browser tie-break, browser "wait for calendar" rather than drop. `promptTitle()` gives
  "Weekly sync" or "Slack huddle".
- `detector.ts` — `Detector`: reducer + `MicAppsSource` + one timer at `nextDeadline`; `setRecording`,
  `setEvents`, `setSilenced`, `promptClosed`, `onAction`, `onError`. This is what 7.3 wires to notifications,
  recording state and `CalendarCache`.
- `source.ts` — `MicAppsSource` (`list`, `watch(onApps, onError)`), `FixtureMicAppsSource` (in-memory,
  `setApps`). `sidecar-source.ts` (`@oat/detection/node`) — `SidecarMicAppsSource` over the sidecar, same
  process handling as `SidecarCalendarSource` (ready timeout, EOF → SIGTERM → SIGKILL, crash → `onError`,
  malformed `apps` line → `onError`, unknown types ignored).
- `timeline.ts` — `DetectionTimelineSchema` (strict zod), shorthand calendar events (`timelineEvent`),
  `runTimeline()` on a virtual clock (inputs at `at`, ticks at every deadline), `compactAction()`.

**Fixtures** `fixtures/detection/*.json` (11): one timeline per rule group, each with an exact `expect` list —
`zoom-basic`, `short-grab`, `debounce-flap`, `rate-limit`, `recording`, `silenced`, `browser-no-calendar`
(declined/cancelled/all-day/>15 min late/far-future events), `browser-calendar` (waits for window; one prompt
per event), `calendar-names` (in progress / late join / starting in 75 s beats a solo block / timeout),
`helpers` (folding, prefix rule), `sidecar-replay` (≈5.5 s, used by the Swift tests and the Node int test).
Same files feed the sidecar's `--fixture` (it reads only `steps[].at` + `micApps`).

**Tests.** `timeline.test.ts` runs every fixture and asserts a rule → fixture coverage map; `detect.test.ts`
pins exact boundaries (delay, debounce, rate limit, timeout), purity, pid changes, calendar arriving while a
browser waits, `nextDeadline`; `apps.test.ts`; `detector.test.ts` (fake timers); `sidecar-source.test.ts`
(scriptable fake sidecar, any OS); `sidecar-source.int.test.ts` (real binary, `--fixture` only: list, watch
replay, and `Detector` over the sidecar matching the fixture's actions within 1 s). Swift `MicAppsTests` (11):
CLI parsing, JSON, differ, poller error de-dup, fixture replay of `sidecar-replay.json` with an injected
clock, every shared fixture parses, path helpers.

**Note for CI:** the int test needs `native/oat-audio/.build/release/oat-audio` or `OAT_AUDIO_BIN`
(skipped otherwise); since main's `swift:release` ci step it runs in `pnpm run ci` on macOS.

**Review round 1 fixes (supersede rules 3–4 and 7 above; `detect.ts` header has the current list):**
1. *Defer, don't cancel.* Gates are split: **permanent** (recording, app silenced, current event already
   prompted) mark the presence `done`; **temporary** (a prompt on screen, rate limit) keep it `pending`, and
   `nextDeadline` adds `lastPromptAt + rateLimitMs` while a deferred presence holds the mic (prompt timeout was
   already a deadline). The calendar event is looked up when the prompt is finally shown, so a deferred Zoom
   gets its event name. Fixture `deferred-prompt.json` (huddle prompt, Zoom 85 s later → prompted at the limit,
   named "Planning"); unit tests for exact expiry, on-screen-prompt deferral, deferred app leaving first.
2. *Per-app `minHoldMs`* in `MeetingApp` (`MESSAGING_MIN_HOLD_MS` = 15 s for Slack, WhatsApp, Telegram, Signal,
   Discord, Skype; 0 for Zoom/Teams/FaceTime/Webex/others/browsers). A current calendar event skips the hold.
   Fixture `voice-note.json` (5 s WhatsApp note, 8 s Slack clip, 20 s Chrome dictation during an in-person
   recording → nothing; a real WhatsApp call prompts at 15 s).
3. *Eligibility gates the meeting span.* A presence becomes `eligible` once, while holding the mic: delay
   passed, min hold passed (or event), browsers only with an event — independent of recording/silence, so a
   call during a recording still counts. Only eligible presences open/extend a span and end it; short grabs and
   calendar-less browser use never emit `meetingEnded`. `meetingEnded` now carries `prompted` and
   `recordingStartedDuringMeeting` (a recording that started at/after the span's `startedAt` — i.e. after the
   first eligible app took the mic — or while it was open), plus `recording`. **Contract for 7.5:** auto-stop
   only when `recording && (recordingStartedDuringMeeting || prompted)` (documented in `detect.ts`).
   Tests: `recording.json` (FaceTime during an in-person recording → `recordingStartedDuringMeeting: false`),
   `voice-note.json`, unit tests for before/during/early-start recordings.
Optional ones done: `resolveMeetingApp` prefers the outer `.app` (`appBundleId`) over the helper's own id;
Meet PWA entry dropped (PWAs resolve to their browser); `mic-apps` watch queue uses
`autoreleaseFrequency: .workItem`; `rebaseClock` shifts stored times when the wall clock steps back > 60 s
(smaller steps are clamped as late input) — chosen over a monotonic clock because macOS's monotonic clock
stops during sleep and calendar matching needs wall time; `promptedEventIds` pruned once events end.
Deferred: Core Audio property listeners instead of 1 Hz polling (D-21 chose polling).
Fixtures now 13 (+`deferred-prompt`, `voice-note`); `@oat/detection` unit tests 64.

## Review

Reviewer, 2026-11-14 — **changes** (three behavioural fixes in the reducer/data; the sidecar and design are sound).

Re-ran (safe only): `@oat/detection` vitest 54/54 pass. Nothing run against Core Audio; `mic-apps` not run
without `--fixture`. Core Audio usage checked by reading: process list (size → data, truncated to returned size),
`IsRunningInput` read first so PID/BundleID are only read for mic users, BundleID `CFString` taken +1
(`takeRetainedValue`, correct), per-pid `appBundleId` cache pruned every poll — no leak over long runs. 1 Hz
polling matches D-21. Self-exclusion holds: allowlist-only, Oat's own sidecar/app (null / `com.oat.desktop`)
never resolves (tested), plus the recording gate. Tests are meaningful (exact-boundary, purity, fixture `expect`
lists, real-binary fixture replay).

Must fix:
1. `packages/detection/src/detect.ts:264-271` — the *temporary* gates (a prompt on screen, the 2-min rate limit)
   set `candidate = 'done'`, so a real call that starts within 2 min of another app's prompt never prompts for
   its whole duration (e.g. quick Slack huddle or a WhatsApp voice-note prompt at 10:00, the scheduled Zoom at
   10:01 → silent for an hour, and its calendar name is lost). Fix: only permanent gates drop (recording,
   silenced, event already prompted); for "prompt on screen" / rate limit keep the candidate `pending` and have
   `nextDeadline` (`:319-340`) add `lastPromptAt + rateLimitMs` (and re-evaluate on `promptClosed`/dismiss), still
   requiring the app to hold the mic at that moment. Add a fixture for it.
2. `packages/detection/src/apps.ts:56,62-65` with `detect.ts:254` — Slack (clips), WhatsApp, Telegram, Signal
   (and Discord voice messages) hold the mic for voice notes/clips well over the 2 s delay, so recording a voice
   note prompts "WhatsApp call" / "Slack huddle". Fix: per-app `minHoldMs` in `MeetingApp` data (e.g. 15 s for
   messaging apps + Slack; 0 for Zoom/Teams/FaceTime/Webex), used instead of `promptDelayMs` when larger; a
   calendar event overlapping may short-circuit it. Pin with a fixture.
3. `packages/detection/src/detect.ts:219-245` — a `meeting` span opens for *any* presence (incl. a 1 s grab and a
   calendar-less browser mic use) and `meetingEnded.recording` is just "Oat is recording now". During an
   in-person recording (no meeting app), a voice note / Chrome dictation emits `meetingEnded{recording:true}`,
   which 7.5 auto-stop would act on. This action is the contract 7.5 consumes, so fix it here: track whether
   recording *started while this span was open* (or whether the span was prompted / lasted past the delay) and
   emit that (e.g. `recordingStartedDuring`, `prompted`), and document that 7.5 must use it. Test it.

Optional:
- `apps.ts:155-157` — prefer `appBundleId` (the user-visible outer `.app`) over the helper's own `bundleId` when it
  resolves: a native app whose embedded helper carries a browser-prefixed id (WebView2/CEF-style) would
  otherwise be classed as that browser and wait for a calendar event. Confirm Teams 2 helper ids at the checkpoint.
- The Meet PWA id (`apps.ts:69`) likely never shows: Chrome PWAs capture in Chrome's audio-service helper, so Meet
  PWA calls resolve to Chrome (browser). Harmless, but don't rely on it.
- `main.swift` mic-apps queue: create it with `autoreleaseFrequency: .workItem` so any ObjC autoreleases
  (`Bundle(path:)`) drain per poll in a days-long `watch`.
- `detect.ts:155` — if the wall clock steps backwards, `n` is pinned to the old `state.now` and debounce/delays
  freeze until real time catches up; consider a monotonic clock in `Detector` or resetting on a large jump.
- `promptedEventIds` grows for the app's lifetime; prune ids of events that ended.
- Event-listener mode (`kAudioHardwarePropertyProcessObjectList` + per-process `IsRunningInput` listeners) would
  cut idle IPC and latency; fine to defer, 1 Hz polling is what D-21 chose.
