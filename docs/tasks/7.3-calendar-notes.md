# 7.3 — Meeting notes from calendar events (+ detection wiring)
status: done
milestone: M7 · deps: 3.4, 7.1, 7.2, 7.4 · branch: task/7.3-calendar-notes

## Goal
Upcoming meetings are one click from notes: the desktop shows today's events, "Start notes" creates a meeting note
pre-filled from the event (title, time, attendees as participants, conference link), and meeting detection's
"Start notes?" prompt does the same for the current event.

## Context
SPEC §3.1 (Detect), §4 Calendar/Detection, D-21, `@oat/calendar` (CalendarSource, SidecarCalendarSource fixture
mode, GoogleCalendarSource via web API `/api/calendar/upcoming`), `@oat/core` calendar helpers
(currentMeetingFor, startingSoon), `@oat/detection` (Detector, MicAppsSource fixture/sidecar), `apps/desktop`
(meeting view 3.4, RecordingService, notifications), `apps/web` Home "Upcoming" (7.4).

## Scope
In:
- Desktop: "Upcoming" list in the sidebar (today + tomorrow; from EventKit via sidecar when permitted, else
  Google via web API, merged/deduped); event → "Start notes" creates the meeting doc with title, start time,
  calendar_event_id, participants (calendar source), conference link in header; joining an already-created note
  for the same event reopens it (no duplicates).
- Detection wiring: run `Detector` in main (MicAppsSource sidecar in prod, fixture in dev/e2e via env); on
  `prompt` show a native notification + in-app banner "Start notes for <event or app>?" → creates/opens the note
  and starts recording; "Not now" / silence app; respects D-21 rules; `meetingStarting` notification ~1 min
  before events with attendees (startingSoon).
- Web Home "Upcoming": "Start notes" creates the meeting note on web (no recording) with the same prefill.
- Permissions UX: if Calendars permission not granted, a clear "Connect calendar" call-to-action (sidecar status) —
  never prompt automatically.
- Tests: unit (dedupe/merge, prefill mapping), desktop e2e with calendar fixture + mic-apps fixture timeline →
  notification banner appears → accept → note created with attendees + recording running (FileSource);
  web e2e Start notes from Upcoming. Screenshots.
Never run real EventKit / mic-apps / capture — fixtures only.

**Main process (`apps/desktop/src/main`).**
- `calendar-setup.ts`: sources per config. Packaged: `SidecarCalendarSource` (EventKit) + `SidecarMicAppsSource`
  with the bundled binary (OAT_AUDIO_BIN stripped, `sidecarLocateOptions`). Dev: **off** unless `OAT_CALENDAR=
  eventkit|fixture:<file>` / `OAT_DETECTION=sidecar|fixture:<timeline>`; fixtures run in process
  (`FixtureCalendarSource` from JSON / `{access, events}` / `.jsonl`; `ReplayMicAppsSource` replays a detection
  timeline's `steps[].micApps` from detector start). `request-access` is wired only to the "Connect" click; a
  fixture's "Connect" grants in memory (testable, no macOS prompt).
- `calendar-service.ts`: `CalendarCache` over the Mac source (−24 h … +3 d) + Google via
  `GET /api/calendar/upcoming?days=2&limit=50` (bearer; every 5 min, on sign-in, on refresh), merged with
  `mergeCalendarEvents([mac, google])` (Mac copy wins). Snapshot = `upcoming(now … start of the day after
  tomorrow)` mapped to `UpcomingEvent` (+ `documentId` of the existing note via `noteFor(noteKeys(event))`),
  emitted only on change (fingerprint) incl. a 60 s tick. "Meeting starting": `startingSoon` (D-21, notifiable =
  timed, attended, titled, other attendees) once per event id, re-armed with `nextStartingSoonAt` (timer capped
  at 10 min). Stopped at quit (`will-quit`): in-flight API reads are aborted and nothing runs afterwards — a late
  result reading the already-closed local database threw in main, and Electron's modal "JavaScript error" dialog
  kept the process alive (found as an intermittent e2e teardown timeout; `sample` showed `NSAlert runModal` from a
  timer). Note lookups never throw (a closing database = "no note").
- `detection-service.ts`: `Detector` (all D-21 rules in `@oat/detection`) runs while signed in; inputs:
  recording state (from `RecordingService.onStatus`), merged events, silenced apps (`<userData>/detection.json`).
  One prompt at a time (`prompt:changed`): detector prompts (replace a "starting" one), "starting" prompts (not
  while recording/another prompt, 2 min timeout). Native `Notification` (click = Start notes, then focus + open the
  note via `notes:open`); in e2e nothing is shown — recorded on `globalThis.__oatNotifications`. `respond`:
  start → host `startNotes` (note from the event if any — continued only if `cannotContinue` is null, else a new
  note — then `recording:start` with the default/dev input) → `promptClosed`; dismiss; silence (persisted,
  detector dismisses). Stale prompt ids → `invalid_state`.
- `meeting-notes.ts`: `fromEvent(event)` → existing note for the meeting key (mine first, then a shared one;
  trashed ignored) or a new private note in the personal workspace: title (or "Meeting, <date>"),
  `calendarEventId` = meeting key, `platform` = conference provider, participants `source: calendar` (everyone but
  me, organizer first, deduped by email, ≤ 300; `notePrefill` in `@oat/calendar`, shared with the web);
  concurrent calls for one event share one creation. `get` adds `calendarEvent` (looked up by key in the
  calendar). `recordedHere` / `cannotContinue` (D-24) now also allow a meeting with no start and no transcript.
  `meeting-persistence.beginMeeting` sets `started_at` on the first recording of such a note.
- Bridge: `packages/core/src/bridge-calendar.ts` (spread into the contract): invoke `calendar:get|refresh|connect|
  start-notes`, `prompt:get|respond`; subscribe `calendar:changed`, `prompt:changed`, `notes:open`;
  `meetingNoteSchema.calendarEvent` (nullable, default null).

**Web.** `POST /api/calendar/notes {eventId, workspaceId}` (`server/calendar-notes.ts`): the event is looked up
server-side in the user's own Google calendar (`findCalendarEvent`, −1 d … +21 d) — never from client data; 404 if
absent. In one transaction with a per-user+meeting advisory lock: reuse a readable live note with that key (mine
first; `canReadDocument`, so another member's private note is never handed out) → 200, else create (authz
`workspaceForCreate`: members, not viewers) private root meeting doc + meeting row (key, platform) + calendar
participants → 201. Home "Upcoming" row: "Start notes" (hidden for viewers, disabled until hydrated) → POST with
the current workspace → `/d/<id>`; errors toast. `denies('POST /api/calendar/notes')` in
`calendar-notes.int.test.ts` (viewer 403, other workspace 403/404, someone else's event 404, other's private note
not reused, anonymous 401, cross-site 403).

## Review

Reviewer, 2026-11-15 — **changes** (two small fixes; the web authz, key design, D-21 wiring and quit fix are sound).

Read the diff + screenshots only; nothing run (no EventKit, mic-apps or capture).

Checked and fine: `POST /api/calendar/notes` resolves the event server-side from the caller's own Google calendar
(404 otherwise), never trusts client data; reuse filters every key match through `canReadDocument` (same check as
search/chat/sharing), so another member's private note with the same `calendar_event_id` is never returned and a
crafted UID only ever yields notes the caller can already read; create goes through `workspaceForCreate`; advisory
lock is per user+key. D-31 key (`ical:<UID>@<UTC ISO start>`) is per occurrence for recurring series and
timezone-independent. Packaged config hard-codes eventkit/sidecar before any env is read (no fixture/e2e path);
fixtures for `prompt:respond` go through the same `resolveInput` gate as `recording:start`. Recording only starts
from an explicit banner/notification click; Upcoming "Start notes" never records. Notification text = event title
(or "<App> meeting") + app name, no attendees. "Starting" prompt suppressed while recording; detector owns the rest.
Quit fix (`#stopped` guards on `#merge`/`#emit`, abort of in-flight reads) addresses the observed dialog hang.

Must fix:
1. `apps/desktop/src/main/meeting-notes.ts:150-153` (+ `findByCalendarKeys` `:159-170`, used by `index.ts:531-535`)
   — the D-24 refinement ("no start + no transcript = recordable here") applies to *any* editable note, including a
   teammate's workspace-visible note that `fromEvent` reuses ("mine first, then shared"). When both are prompted
   for the same meeting, each Mac sees `started_at = null` until sync catches up and both record into one meeting
   (two devices writing parts/segments to the same meeting — exactly what D-24's "only where the audio is" rule
   prevented). Fix: allow the no-start case only when `doc.ownerId === userId` (another person's never-recorded
   note → `cannotContinue` non-null → `startNotes` already falls back to a new own note); add a unit test.
2. `apps/desktop/src/main/index.ts:523` / `detection-service.ts:79,280` — "Don't ask for <app>" is stored in one
   `<userData>/detection.json` shared by every account on the Mac and read once at construction, so it leaks
   across sign-ins (7.2 semantics: the silence list belongs to the user, like the rest of their local state).
   Fix: key the file by user id (e.g. `detection-<userId>.json` or inside the per-user data dir) and reload
   `#silenced` in `start()` for the signed-in user.

Optional:
- `calendar-service.ts:186-190,256-269` — after `stop()` a later `authChanged()`/`refresh()` (e.g. sign-out
  during quit) still starts a Google fetch on the *fresh* controller; return early in `#refreshGoogle` when
  `#stopped` (and don't recreate the controller).
- `calendar-service.ts:270` — a Google fetch started for user A that finishes after a switch to user B only checks
  `signedIn()`; compare the user too.
- Rescheduling one occurrence changes its start → its key; the existing note loses its "Scheduled/Join" line and
  "Upcoming" offers a second note. Acceptable for now; worth a line in D-31 or IDEAS.
- All-day events: EventKit local midnight vs Google date-only may give different keys (dedupe and notes). Low impact.
- A note started on the web and one started on the desktop before sync pulls it can still duplicate (desktop
  dedupe is local only); fine as a known limitation.
- `detection-service.ts:202` — a detected prompt replacing a "starting" one also covers the D-21 rate limit only
  via the detector; fine, just note it in the header.
