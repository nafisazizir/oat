## Design notes

### Recommendation (short)
**Keep D-7: durable/background work runs on eve** — with one shift in how we use it: deterministic pipelines
(post-meeting, digests' data gathering) are **plain `"use workflow"` / `"use step"` functions started by our
own route with `start()` (no model call)**; eve *sessions* (model-driven turns, tools, channels like Slack)
only where a model must decide. eve runs fully offline on our stack (proved below), its durability is the
open-source Workflow SDK on our own Postgres, and the step bodies stay our plain functions, so lock-in is the
~200 lines of glue. Guardrails in the D-29 proposal (pin the exact version, own run log, telemetry off,
lock-stale window, Node ≥ 24).

### How the evaluation was done
- Installed `eve@1.0.0-rc.18` (latest; `npm view eve`: 289 versions, rc.4 → rc.18 between 4 and 14 Nov 2026)
  in a scratch dir, then in the workspace package `agents/`, and read the bundled docs in
  `node_modules/eve/docs/` (README, getting-started, agent-config, concepts/execution-model-and-durability,
  guides/deployment/{index,workflow-worlds,self-hosting}, tools/{index,workflows}, channels/{eve,custom},
  schedules, evals/index, reference/{cli,telemetry}, guides/auth-and-route-protection,
  guides/instrumentation/otel, connections/index, concepts/built-in-tools) plus `@workflow/world-postgres`'s
  README / `job-lease.d.ts`.
- **Offline probe** (scratchpad, not committed): a 3-step workflow tool + mock LLM, run under macOS
  `sandbox-exec` with *all outbound network denied except loopback* (verified: `curl https://registry.npmjs.org`
  → exit 7; `curl localhost:14010/health` → 200). `eve build` (8.4 s, 10.4 MB) and `eve start` worked;
  `POST /eve/v1/session {"message":"mock:tool post_meeting {...}"}` → the mock LLM called the tool → steps ran,
  a step throwing `RetryableError` was retried once, the turn completed (`turn.settled outcome: completed`).
  Same with the Postgres world on the compose Postgres; then **`kill -9` during a durable `sleep`** and restart:
  the run resumed and finished; completed steps did not run again (probe log: `enhance, index, index(retry),
  notion` — no repeats).
- Then a custom channel route calling `start(workflow, [input])` from `eve/workflow/api`: a deterministic
  2-step workflow ran and `getRun(runId)` returned `completed` + its return value — **no model involved**.
  This is the shape the spike uses.

### Answers
**1. Local/offline with our mock LLM, Postgres, Redis? — Yes.**
- Model: `model` accepts any AI SDK language model (`EveLanguageModel`); agent-config "Use a local model"
  documents `@ai-sdk/openai-compatible` with a `baseURL`. The spike passes `@oat/ai`'s `getModel('fast')`
  (mock LLM at `AI_BASE_URL`/`MOCKS_URL`, or AI Gateway when a key/OIDC is set) through
  `defineDynamic` (resolved per call, so `eve build` needs no AI env; dynamic models set the context window in
  a selection object, the mock isn't in the Gateway catalog).
- Durability store: Workflow "world" — local (files in `.eve/.workflow-data`) or `@workflow/world-postgres`
  (our compose Postgres; own database). Redis: eve needs none; our steps use it (enhance broker, run log).
- **CLI telemetry is on by default** (reference/telemetry: sends command/OS/version + hashed project id to
  Vercel) → every script sets `EVE_TELEMETRY_DISABLED=1` (D-11).
- **`eve build` fetches the AI Gateway model catalog** (`GET https://ai-gateway.vercel.sh/v1/models/catalog`,
  unauthenticated, for context windows; found in `dist/src/compiler/model-catalog.js` after an online build
  left `.eve/cache/model-catalog.json` with the full catalog). No env switch; it is skipped while that cache
  is < 5 min old, and offline it only degrades to a build warning. → `agent:build` / the test harness
  (`src/cli/build.ts`) seed an empty fresh cache first, and the agent sets `modelContextWindowTokens`
  itself. After that change a build with no cache leaves the seeded (0-model) catalog in place.
- Gotcha found: the shared `mocks` container predates 6.2's tool loop (`mock:tool …` was echoed back as text),
  so tests use in-process `startMocks()`; the container needs `pnpm dev:build` from main.

**2. What infra does durability need?** No Vercel. Every session/workflow is a Workflow SDK run; the world
stores the event log, step results, hooks and queues the resumption:
| World | Storage | Processes | After an eve upgrade |
|---|---|---|---|
| local (default for `eve start`/`eve dev`) | files `.eve/.workflow-data` (persistent volume) | one | in-flight runs **stranded** |
| `@workflow/world-postgres` (spike) | Postgres (`workflow`, `workflow_drizzle`, `graphile_worker` schemas; `bootstrap` migrates) | any replicas | in-flight runs **stranded** |
| Vercel Workflow | managed | managed | runs stay on their deployment; idle sessions hand off |
- The server is a Nitro node server (`eve build` → `.output/`, `eve start`); a proxy must forward `/eve/` and
  `/.well-known/workflow/`. Or mount in Next.js (`withEve`) / as a Vercel service next to `apps/web`.
- Postgres world reads `WORKFLOW_POSTGRES_URL`, **else `DATABASE_URL`** — it would put its schemas in the app
  DB; we give it its own database (`oat_workflow`, `pnpm --filter @oat/agents world:bootstrap`).
- Crash recovery (observed + `job-lease.d.ts`): Graphile Worker keeps a dead process's job lock for 4 h; the
  world renews/releases locks itself, by default after a **300 s** stale window (≈ 8 min to resume a run whose
  process was SIGKILLed — in the probe the run sat parked until restarted with a short window).
  `WORKFLOW_POSTGRES_JOB_LOCK_STALE_SECONDS=30` → ≈ 45 s (the test uses 2).
- Replay semantics (execution-model doc): completed steps are never re-run; an interrupted step re-runs, so
  side effects need idempotency keys (our steps have them). eve never retries *tools*; *workflow steps* retry
  with backoff (`RetryableError {retryAfter}` = durable timer, `FatalError` = no retry).
- **Stranded runs**: on local/Postgres worlds only the eve version that started a run can replay it; an
  upgrade leaves in-flight runs dormant (root sessions retire on timeout/next message, workflow runs are
  cancelled). → pin the exact version; upgrade only with no in-flight runs.
- Node ≥ 24 (eve `engines`); our CI/.nvmrc is 24, root `engines` still says ≥ 22.13.

**3. Tools / connections.** A tool is a file `agent/tools/<name>.ts` default-exporting
`defineTool({ description, inputSchema (zod), execute(input, ctx) })` (runs app-side, not in the sandbox;
eve never retries a throwing tool). `defineWorkflowTool` adds durable waits (`execute`), background tasks
(`task`) or resumable tasks (`serve`), `ctx.ask` for HITL. Connections are files in `agent/connections/`
(`defineMcpClientConnection`, OpenAPI), credentials stay app-side. Our `packages/ai/tools` are plain
functions, so each wraps 1:1 in a `defineTool`. Approvals: `approval` option per tool.

**4. Scheduling.** `agent/schedules/<name>.(md|ts)`: `defineSchedule({ cron, timezone?, content | run })`.
Vercel → Vercel Schedules (beta; failed invocations not retried; Hobby ≥ 15 min). Self-host → the runner in
`eve start` (run it on one replica, `EVE_SCHEDULES_DISABLED=1` on others); `eve dev` never fires them (a
dev-only dispatch route does). Runtime-created schedules are experimental.

**5. Observability.** Per-session NDJSON event stream (`/eve/v1/session/:id/stream`), local trace store +
`eve traces` (span tree, tokens, cost), `eve logs`, OpenTelemetry (`agent/instrumentation/otel.ts`), Vercel
Agent Runs on Vercel; workflow runs/steps/events are rows in the world's Postgres schema; `getRun(runId)`.
Caveat (otel doc): the default trace policy also drives run-data retention — outside development, payloads of
private/unknown-audience sessions are deleted when the run ends. → the product's run log must be our own
table, not the world's records.

**6. Cost / lock-in.** Apache-2.0; durability is the open-source Workflow SDK + Nitro — we ran it with zero
Vercel involvement. Authored glue uses eve APIs (`defineAgent`, `defineChannel`, `eve/workflow`), but the step
bodies are our plain functions (`agents/src/post-meeting/steps.ts`), so leaving eve means rewriting
`agent/lib/post-meeting.ts` + `agent/channels/jobs.ts` (~170 lines, plus `agent/agent.ts`) onto the Workflow SDK directly or onto
the 6.1 queue. Footprint: `eve` 41 MB + rolldown 18 MB in node_modules (dev/server only, not in `apps/web`);
build 4–10 s, output 25.6 MB (includes the web modules the steps reuse). Biggest cost is **release churn**
(rc, several releases a day) + stranded runs on upgrade. Prod pricing of Vercel Workflow is a 9.6 checkpoint.

### What the spike does (`agents/`, package `@oat/agents`)
```
POST /jobs/post-meeting {meetingId, workspaceId, pushDelayMs?}
     Bearer OAT_AGENTS_TOKEN | OAT_AGENTS_TOKEN_PREVIOUS (≥ 32 chars; none valid → 503); no own Workflow DB → 503;
     meeting not in workspaceId (or unknown) → 404; else start(postMeetingWorkflow) → 202 {runId}
postMeetingWorkflow ("use workflow")               agent/lib/post-meeting.ts
  loadMeeting ─ step   → MeetingRef; missing / deleted / other workspace → FatalError (no retries)
  enhance ─ step       → web enhance job as the note owner, key post-meeting:<runId> (chained on failure);
                         skipped if a completed enhancement exists; another live run (incl. our own,
                         orphaned by a crash) → `busy` → durable sleep(busyRetryMs) and ask again; once
                         that run is stale (D-26) it is settled failed and a fresh run starts
  index ─ step         → @oat/indexing runJob(document): action items (8.4) + chunks (6.1), idempotent
  [sleep(pushDelayMs)] → durable wait (product knob)
  notion ─ step        → web sendToNotion if integration.settings_json.autoPush === true; not connected /
                         off / no target / reconnect → skipped; notion_busy / rate_limited → `busy` (as above)
  busy for > busyDeadlineMs (D-26 staleness + 60 s = 4 min; wall clock from the steps' answers)
                       → run fails: "gave up after waiting N s: <reason>"
  recordRun ─ step     → per-meeting run log (Redis list, newest first, 20 kept, 30 d), also on failure
GET /jobs/post-meeting/runs/:runId → world's record (status + return value)
GET /jobs/post-meeting/:meetingId  → run log
```

- `src/post-meeting/web.ts` — **the spike's seam into apps/web**: re-exports `startEnhancement`,

- `src/post-meeting/context.ts` — lazy per-process deps from env (DB, Redis broker, `@oat/ai`, Better Auth

- `agent/agent.ts` — `defaultTools: false` (no sandbox/shell), Postgres world, model via `@oat/ai`.
- `src/cli/bootstrap-world.ts` — `world:bootstrap`: creates `oat_workflow` if missing + runs the world's

- **Int test** `src/post-meeting/post-meeting.int.test.ts` (real `eve build` + `eve start` child process):

  hit the mock over HTTP, notes + transcript chunks, `action_item` rows = the tasks in the enhanced body,

### eve vs our worker (6.1 Redis queue + AI SDK)
| | eve (Workflow SDK, Postgres world / Vercel Workflow) | 6.1 queue + worker + AI SDK |
|---|---|---|
| Durability | Event-sourced runs; each step's result recorded, replayed on resume; durable `sleep`, hooks, webhooks, `ctx.ask` | Job-level only: a job re-runs from the top; step checkpoints, waits and HITL would be ours to build (run table + state machine) |
| Retries | Per step, backoff, `RetryableError{retryAfter}` / `FatalError`; dead-process recovery via lock renewal (300 s default, tunable) | Per job, exponential backoff, lease + heartbeat, `failed` after N; dead-worker recovery = lease expiry (2 min) |
| Local dev | `eve start`/`eve dev` + Postgres world on compose; offline proved; Node ≥ 24; build step (4–10 s) | `tsx` worker, no build; already in `pnpm dev` and compose (`worker`) |
| Testing | Real server in int tests (≈ 40 s incl. build); `mockModel`/`eve eval` + tool stubs for model-driven agents; steps unit-testable as plain functions | Fastest: `processOnce()` in-process; no harness for waits/HITL because there are none |
| Ops | Extra service (or `withEve` in Next / Vercel service); proxy `/eve/` + `/.well-known/workflow/`; own DB; stranded runs on upgrade; schedules runner on one replica | One long-running worker process; on Vercel it needs a host or cron/queue adaptation (prod hosting undecided) |
| Observability | Event streams, traces (`eve traces`, OTel, Agent Runs), run/step rows | Our logs + `failures()` hash; would need building |
| Agents (model loop, tools, channels, schedules) | Built in: sessions, tools, MCP, Slack/… channels, schedules, evals | Would be built from the AI SDK loop (6.2) + our own channel/schedule code |
| Lock-in / maturity | Apache-2.0, self-hostable; API surface is eve's; **1.0 RC, very high release churn** | None; all ours; mature for what it does (debounced dedup jobs) |
| Fit: post-meeting | Good: steps map 1:1, durable delay before auto-push, retries per step, HITL later ("approve push?") | Workable as one idempotent job, but a delay/approval needs new machinery |
Verdict: keep the 6.1 queue for what it is good at (debounced, deduplicated re-index jobs following
`change_log`); use eve for multi-step, waiting or model-driven background work.

### Proposed decision text (superseded: the accepted D-29 on `main` folds in review items 3–5)

## Review

**Reviewer, 2026-11-15, round 1 — verdict: `changes`.** Read the task file + `git diff $(git merge-base main
task/8.2-eve-evaluation)..task/8.2-eve-evaluation`, the eve docs and the installed `eve`/`@workflow/*` dist.
The evaluation is thorough and the spike is well shaped (plain step bodies, explicit web seam, offline proved);
two code problems undercut the claims the recommendation rests on.

1. **Retry budget breaks durability in the step that matters** — `agents/src/post-meeting/steps.ts:99,111`,
   `agents/agent/lib/post-meeting.ts:63-72`. `RetryableError` attempts count against the Workflow SDK's default
   `maxRetries` 3 (eve's bundled workflow runtime: attempts = `step_started` count, fail at `> maxRetries+1`),
   so a "busy" enhance gives up after ~4 × 5 s. A crash *during generation* leaves the row `generating` until
   D-26's 3-min staleness → the re-run step exhausts its retries → the run fails. Same when the user is
   enhancing by hand at meeting end (the likely 8.3 trigger moment). Fix: have the step return
   `{ busy: true }` and loop in the workflow body with a durable `sleep` up to a deadline > D-26 staleness
