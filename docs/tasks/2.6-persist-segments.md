# 2.6 — Desktop SQLite cache + outbox → API → Postgres
status: done
milestone: M2 · deps: 1.5, 1.6, 1.8, 2.5 · branch: task/2.6-persist-segments

## Goal
Transcript segments (and the meeting/document rows they belong to) are persisted locally the moment they're
final and reliably reach Postgres via the D-19 sync mechanism — the first real slice of desktop sync.

## Context
D-19 (trigger-driven outbox, version acks, disposable cache, single writer WAL), D-22 (server change_log),
SPEC §6, `research/granola/storage-sync.md` (reference). `@oat/db` (server schema, readChanges), `@oat/core`
permissions, `apps/web` route-handler conventions + bearer auth from 1.6/1.8.

## Scope
In:
- `packages/local-store` (`@oat/local-store`): SQLite via `better-sqlite3` (Electron rebuild handled in
  apps/desktop with `@electron/rebuild` or use `node:sqlite` if adequate — decide + note), schema version table,
  migrations, wipe-and-resync on corruption/too-new/failed migration, WAL, single writer; tables mirroring the
  synced server tables needed now (workspace, document, meeting, participant, transcript_segment,
  audio_recording [local-only]) + `outbox(version, table, row_id, op)` filled by triggers + `sync_state`.
- Push: `POST /api/sync/push` (apps/web): batch of outbox entries with row payloads + base versions; server
  validates (zod), authorises per row via `@oat/core`, upserts (segments: insert-or-replace by id within the
  same meeting only), returns acked versions + per-row conflicts (409 semantics per row). Client deletes acked
  outbox rows; retries with backoff; idempotent.
- Pull (minimal now, full in 3.5): `GET /api/sync/pull?cursor=` using `readChanges` filtered to workspaces the
  user can read, returns rows; client applies in one tx with "applying remote" flag (no echo).
- Desktop wiring: RecordingService writes finals + meeting/doc rows to local-store; SyncService runs push on
  change + interval, exposes status via bridge.
- Tests: local-store unit (triggers, migrations, wipe), API int (authz deny cases, idempotent replays,
  cross-meeting id spoofing rejected), property-style test: random sequences of local writes + network
  failures → server converges to the same final segments with no duplicates.
Out: conflict-copy UX + SSE (3.5).

## Design notes
(implementer, 2026-11-14)

**SQLite library: `node:sqlite`, not `better-sqlite3`.** Electron 45 ships Node 24.22 with `node:sqlite`
(SQLite 3.53) built in; vitest runs on Node ≥ 22.13 where it is unflagged too. It covers what we need
(sync API, transactions, triggers, WAL, `PRAGMA`s), so there is no native module, no `@electron/rebuild`,
no ABI mismatch between the test Node and Electron, nothing in `onlyBuiltDependencies`. electron-vite keeps
`node:sqlite` external (checked in `out/main/index.js`). Trade-off: it is still "release candidate" in Node 24
(API is stable enough for our use; it prints an ExperimentalWarning once) and has no SQLCipher — encryption
at rest relies on FileVault (SPEC §6). *Proposed DECISIONS entry (orchestrator):* "D-27 · desktop SQLite =
`node:sqlite` (built into Electron's Node), revisit if we need SQLCipher or a worker-thread reader pool."

**Protocol (`packages/core/src/sync.ts`, `@oat/core/sync`)** — zod shapes shared by web (validates) and
local-store (produces): rows in camelCase + ISO timestamps; `SYNC_PUSH_TABLES` (document, meeting,
participant, transcript_segment) / `SYNC_PULL_TABLES` (+ workspace) / `SYNC_PULL_SCOPE` (bump when the pull
grows → clients restart their cursor). `sameDocumentContent()` compares TipTap JSON ignoring key order
(jsonb) and block ids. Push entry = `{version, op:'upsert', table, row, baseVersion?}` |
`{version, op:'delete', table, id}`; result per version = `ok` (+ stored document row) | `conflict` (+ server
row) | `rejected` (`forbidden|not_found|invalid|unsupported`). Pull = `{changes, cursor, hasMore,
workspaceIds}`.

**`@oat/local-store`** (`packages/local-store`)
- `open.ts`: WAL + `synchronous=NORMAL` + FKs; schema version = `PRAGMA user_version`; migrations are an
  append-only SQL list. Wipe (files incl. `-wal/-shm`) and rebuild when: open/`quick_check` fails (corrupt),
  `user_version` > ours (too new), a migration throws (retried once on an empty file; a second failure is a
  bug and throws). Single writer: one connection in the Electron main process behind the single-instance
  lock; node:sqlite is synchronous so statements never interleave.
- Schema (migration 1): `workspace`, `document`, `meeting`, `participant`, `transcript_segment` (mirrors of
  the server, `STRICT`, FK cascades), `audio_recording` (local only, implements `@oat/audio`
  `AudioRecordingStore`), `sync_state` (kv: cursor, scope, known workspaces, owning user), `sync_control`
  (`applying_remote` flag), `outbox(version AUTOINCREMENT, table_name, row_id, op, first_enqueued_at,
  UNIQUE(table,row))`. Per synced table three AFTER triggers do `INSERT OR REPLACE` into the outbox unless
  `applying_remote` → one entry per row, a newer edit gets a newer version.
- `takePushBatch(n)`: parents first (document → meeting → participant → segment, then version), joined
  with current rows; an `upsert` whose row vanished is dropped. `applyPushResults`: delete **by version**
  (an edit made while the push was in flight survives), documents take the server's version (and the server
  row when not edited since), `conflict` → server copy wins the row, our differing text becomes a new private
  page "<title> (conflicted copy)" (pushed like any new doc; identical text → no copy), `rejected` → dropped +
  logged.
- `applyPull(page, sentCursor)` in one tx with `applying_remote`: remote upsert skips rows with a pending
  local entry (our edit is pushed next and resolved by the server); remote delete wins and clears the entry;
  FKs deferred within the page, orphans (parent never arrived/not readable) dropped via
  `foreign_key_check`; upserts whose rows a cascade removed are dropped from the outbox. Workspaces missing
  from `workspaceIds` are dropped with their content; a workspace the user *joined* resets the cursor and the
  page is not applied (`restart`) — its history is behind our cursor (LOG 1.5 note).
- `SyncEngine` (transport-agnostic): run = push batches until empty, then pull pages until `!hasMore`;
  never overlapping; `kick()` debounced 500 ms (not while backing off), 30 s interval backstop, `syncNow()`
  resets backoff; failures: status 0 → `offline`, others → `error`, exponential 1 s → 60 s with jitter;
  401 → `stopped` + `onUnauthorized`; 409 on pull → cursor reset.

**Server (`apps/web/src/server/sync/`, routes `src/app/api/sync/{push,pull}/route.ts`)** on the shared
`apiRoute` (CSRF guard for cookie writes, bearer for desktop, session → actor).
- Push: envelope zod (1..500 entries with versions), then **each entry** parsed on its own (malformed →
  `rejected/invalid`, the batch still applies); one entry per row (an older duplicate is answered `ok`); one
  transaction, parents first, each entry in a savepoint. Authorization via `@oat/core`: new document only
  where `canCreateInWorkspace` (member, not viewer, workspace not deleted), always owned by the actor,
  private, at the root, content through `prepareContent` (editor schema, block ids, Markdown); existing
  document needs `canReadDocument` (else `not_found`, no existence leak) + `canEditDocument` (else
  `forbidden`), same workspace and kind. Stale `baseVersion`: same text → `ok` (replay), else `conflict` with
  the server row; current base → update + `version+1` (row locked `FOR UPDATE`). Meetings/participants/
  segments need edit rights on the meeting's document; a meeting can't be re-pointed at another document,
  a document can't get a second meeting. Segments of one meeting go in as one `INSERT … ON CONFLICT (id) DO
  UPDATE … WHERE transcript_segment.meeting_id = excluded.meeting_id RETURNING id` — ids not returned already
  belong to another meeting → `rejected/invalid` (cross-meeting spoofing never moves or overwrites a
  segment); a failing statement is retried per row. Deletes: segments/participants (idempotent, authorized
  via their meeting); documents/meetings → `unsupported` (trash goes through the documents API).
- Pull: `readChanges` over the actor's (non-deleted) workspaces, last change per row, **current** row or a
  `delete` when gone or no longer readable (`canReadDocument` on the row's document) — e.g. a doc made
  private by its owner disappears from members' caches. Only finals with text travel. Undecodable cursor →
  409 `stale_cursor`; `limit` 1..500.
- `denies('POST /api/sync/push')`, `denies('GET /api/sync/pull')` in `sync.int.test.ts`; entrypoints test
  covers anonymous refusal automatically.

**Desktop.** (Round 1: per-user `oat-<userId>.sqlite`, see below.) `SyncService` = engine bound to the signed-in user (start on sign-in,
stop on sign-out; `sync_state.user.id` — another account wipes the cache first). Transport =
`AuthController.withSession` (bearer stays in main; 401 signs out) + `api.syncPush/syncPull` (30 s timeout;
pulled changes that fail the protocol schema are skipped and logged, never block pulls). `MeetingPersistence`
(`TranscriptPersistence` hook of `RecordingService`): `beginMeeting` before the audio starts creates the
meeting + a private `meeting` document ("Meeting, Nov 14, 3:04 PM") in the personal workspace; if the
workspace isn't known yet it keeps syncing (≤ 10 s; a pull can be briefly empty under the D-22 xmin rule) and otherwise the start fails visibly ("Oat needs to connect
once…"); finals saved as they arrive (empty final = delete), interims never; `endMeeting` stamps `ended_at`.
A store failure becomes a non-fatal `transcript_store_failed` issue (recording continues). `audio_recording`
rows now live in SQLite. Bridge: `MainState.sync` (`state`, `pending`, `lastSyncedAt`, `error`), invoke
`sync:now`. Sidebar line (`data-testid=sync-status`, tokens only): "All changes synced" / "Syncing…" /
"N changes waiting to sync" / "Offline — N changes saved on this Mac" / "Sync problem — retrying".
Dev-only `OAT_SYNC_URL` (config, same https/loopback rules) points sync elsewhere (e2e offline test).

**Tests.** core `sync.test.ts` (6); local-store 31 (open/wipe 6, store 19, engine 6 incl. 25-round property
test with offline / lost-response / 5xx faults); web `sync.int.test.ts` 12 (incl. 6-round property test

**Out of scope touched (noted):** `packages/core` (`src/sync.ts` new — SPEC puts the sync protocol in core;

**Follow-ups (3.5 or later).**
- Lost ack + a further edit of the same *document* gives a false conflict (the replay check only recognises
  an identical resend). Fine for 2.6 (desktop only creates meeting docs); 3.5 could send a per-device push id.
- Pull echoes our own pushed rows back (harmless upserts); 3.5 can skip rows whose change came from this
  device, and add SSE invalidation + per-workspace cursors (joining a workspace currently re-pulls all).
- LOG 1.5 note still open: statement/idle timeouts against xmin stalls, change_log pruning (then
  `stale_cursor` becomes real).
- Resuming a meeting from a previous launch still starts its audio part at offset 0 (offsets are in memory,
  2.5); the `audio_recording` rows are now in SQLite, so the offset can be derived there.
- Signing out keeps the cache (same user keeps unsynced work); a "reset local data" action is not exposed.

**Review round 1 — fixes (implementer, 2026-11-14).** Items 1–3 fixed; 4–5 moved to PLAN 3.5 by the
orchestrator; optional: push-409 no longer resets the pull cursor, out-of-range cursors are 409, a strict-row
int test covers `ownerId`/`visibility`/`version`. Where the notes above say otherwise, this wins:
1. **Wipes (`open.ts`).** Only on `SQLITE_CORRUPT`/`SQLITE_NOTADB` (primary of `errcode`), a non-`ok`
   `quick_check`, a too-new `user_version`, or a migration error that isn't transient. Busy/locked, full,
   I/O, can't-open, read-only, no-memory, perm, protocol → `LocalStoreUnavailableError`, file untouched (test:
   a file held by another connection's exclusive lock throws `SQLITE_BUSY` and keeps its data). The public
   `wipe()` is gone. **Audio index:** `audio_recording` moved out of the cache into `AudioIndex`
   (`<userData>/audio-index.sqlite`, next to `audio/`, shared by all accounts, own `user_version`); never
   wiped — a corrupt index is renamed `*.corrupt-<time>`, transient errors throw (test: rows survive a cache
   rebuild). **Per-user files:** `<userData>/oat-<userId>.sqlite` (`databaseFileFor`). `SyncService.setUser`
   (serialized): sign-out stops the engine and keeps the file open; another account stops the engine,
   awaits `idle()`, closes (keeps) the previous file and opens the new one; while a recording runs the switch
   is deferred until `recordingEnded()` (RecordingService status → idle), and `auth:sign-in` is refused while
   signed in and recording. A file that can't be opened → status `error` "can't be opened right now;
   retrying", retried every 5 s; `MeetingPersistence` then refuses to start a recording with that message.
2. **Poison/oversized entries.** `takePushBatch(n, ~1 MB)` caps by serialized size too (an oversized entry
   goes alone). Push 400/413 → split in halves depth-first (parents still first) until the entry that breaks
   it is alone → parked; 5xx `serverErrorsBeforeSplit` (3) times in a row → same, but singles are parked only
   if another part of the batch went through (otherwise it's an outage: backoff, nothing parked). Outbox
   gained `parked_at`/`park_reason`; parked entries are skipped by pushes, counted in `SyncStatus.parked`
   (bridge `MainState.sync.parked`, sidebar "N changes couldn't sync — kept on this Mac, retrying later"),
   retried after 15 min (`unparkOlderThan`) or when the row is edited again (the trigger replaces the entry,
   unparked). Server: `asRejection` turns any unexpected per-entry error (converter bug, odd Postgres code)
   into `rejected/invalid` (logged); only infrastructure errors (Postgres 08/40/53/57/58, ECONN*/CONNECTION_*)
   fail the request. Tests: oversized (413) and poison (400) isolated + parked with log₂ requests, 5xx outage
   parks nothing, 5xx poison parked; `push.test.ts` for the classification.
3. **Trashed note.** Picked *park and retry* over letting owners write children of a trashed note: the
   edit rule stays in one place (`canEditDocument`, trash = read-only for everyone), nothing special-cases
   trash on the server, and nothing is lost. Every `rejected` result is now parked (never dropped); a pulled
   document upsert that is live and newer than the local copy (restore bumps the version) unparks that note's
   document/meeting/participant/segment entries (`unparkDocument`); an echo of our own write or a move *to*
   the trash doesn't. Int test: real `LocalStore` + engine → segment pushed while trashed is parked → web
   restore → next sync pushes it; Postgres has both segments.

Also found while re-running e2e: `SyncService` re-applied the same user on every MainStore change, and its
own status update is a MainStore change → busy loop at launch (no window). Fixed: re-announcing the same user
is a no-op and unchanged status isn’t re-emitted (test added). **Round-1 checks:** full `pnpm run ci` after
merging main @4c6c3b5: `ci: ok` — every step pass (test:int incl. sync 13, desktop e2e 7/7, web e2e).

*Proposed DECISIONS entry (orchestrator logs D-28):* desktop local store = built-in `node:sqlite`; one cache
file per user (`oat-<userId>.sqlite`), kept on account switch, no switch while recording; cache wiped only on
corruption/too-new/non-transient migration failure; `audio_recording` in a separate never-wiped
`audio-index.sqlite`; outbox entries that are rejected or break a push are parked (counted, retried), never
dropped and never blocking.

## Review
(reviewer, 2026-11-14, round 1. I read the task file and `git diff $(git merge-base main task/2.6-persist-segments)..task/2.6-persist-segments`.
I did not re-run the tests. I checked `node:sqlite` in the repo's Electron binary.)

**Verdict: `changes`.** Items 1–2 must be fixed. Items 3–5 can be fixed here or moved to explicit 3.5 entries in
`PLAN.md`, but they cannot stay only in the design notes.

These are fine:
- **Push authz.** Each entry is parsed with a strict schema, so `ownerId`, `visibility`, `shareToken`, `version`,
  `createdAt` and `folderId` can't be sent; an extra field is `rejected/invalid`. A create checks
  `canCreateInWorkspace` against a non-deleted workspace. The server forces owner = actor, `private` and root,
  and runs content through `prepareContent`. An update needs `canRead` (otherwise `not_found`, so existence
  doesn't leak) plus `canEdit`. The row is locked `FOR UPDATE`. Only title and content change, and the version
  goes up by one. Moving a document between workspaces or changing its kind is refused.
- **Meeting and segment ownership.** A meeting can't be re-pointed to another document (clash check plus the
  unique `document_id`). Segment and participant upserts carry `setWhere meeting_id = excluded.meeting_id`, so
  cross-meeting spoofing never moves or overwrites a row. Deletes are authorised through the existing row's
  meeting.
- **Validation and idempotency.** The envelope allows 1..500 entries under the 4 MB body limit. Replays are
  idempotent: a create, an identical document, segment and meeting upserts, and deletes all come back `ok`.
  Duplicate versions and multiple entries for the same row are answered once.
- **Pull.** Changes are filtered to the actor's workspaces, and each row is the current row or a `delete` when
  the actor can no longer read it. On the client, losing a document cascades locally to its meeting and
  segments, and leaving a workspace drops its content. An undecodable cursor gives 409, which resets the client's
  cursor.
- **Local store.** The outbox triggers fire in the same statement as the write, so a crash can't leave a write
  without its outbox entry. Acks delete by version, so an edit made during a push survives. `applying_remote`
  is set inside the transaction and reset in `finally`, and a rollback restores it. One synchronous connection
  holds the single-instance lock. Wipes only delete `oat.db{,-wal,-shm,-journal}`, never `audio/`.
- **`node:sqlite`.** Checked in `electron@45.3.2` with `ELECTRON_RUN_AS_NODE`: Node 24.22.2, SQLite 3.53.4,
  `journal_mode=WAL` works.

1. **A wipe can destroy data that is not a cache.**
   - `open.ts:92-96` treats *any* error during open or `quick_check` as `corrupt`, and `open.ts:104-111` treats
     any migration error the same way. That includes SQLITE_BUSY (another process, say a dev build sharing
     `userData`), SQLITE_FULL, IOERR and CANTOPEN. The file is then deleted, and with it the unpushed outbox
     (offline transcripts).
   - `audio_recording` (`migrations.ts:107-121`) is local-only data that can't be rebuilt (`offset_ms`/`part`,
     D-24), yet it lives in the disposable file. Any wipe orphans the audio files: corruption, too-new, a failed
     migration, or the account switch in `sync-service.ts:66-69`.
   - The account switch also silently drops user A's unsynced meetings, and the wipe can run while A is
     recording.
   - Fix:
     - (a) Wipe only on `errcode` SQLITE_CORRUPT (11) or NOTADB (26), or when `quick_check` is not `ok`, and
       rethrow everything else. Don't wipe after a migration error caused by I/O or disk-full.
     - (b) Move `audio_recording` to its own small database that is never wiped (for example `audio.db`), or
       make wipes drop only the synced tables, the outbox and `sync_state`.
     - (c) On an account switch, set A's database aside (`oat-<userId>.db`, one file per user) instead of
       deleting it. Await `engine.idle()` first, and refuse the switch while a recording is active.
   - Add tests: a busy or locked file is not wiped; `audio_recording` survives a wipe.

2. **One bad entry blocks the whole outbox forever.**
   - `sync-engine.ts:211-216,249-251` with `store.ts:451-456`: a failed push is retried with the same
     parents-first batch.
   - So any request-level failure that the batch's content causes repeats on every retry. Examples:
     - 413: 500 segments of up to 10,000 characters (`core/src/sync.ts:122`) far exceed the 4 MB
       `MAX_BODY_BYTES`, and `contentJson` (`sync.ts:49`) has no size limit, so a large conflicted copy is
       enough.
     - 400.
     - A server error that `push.ts:173-174` rethrows (any Postgres code other than 22/23, a bug in
       `toMarkdown`).
   - Every later transcript then stays unsynced while the status reads "Sync problem — retrying".
   - Fix:
     - Cap batches by serialized bytes (about 1 MB) as well as by count.
     - On 400 or 413, or after about 3 consecutive 5xx for the same batch, split the batch in half until the
       bad entry is alone. Then drop that entry or park it, and log it.
     - On the server, have `guarded` turn unexpected per-entry errors into `rejected/invalid`, and rethrow only
       connection, serialization and deadlock errors (classes 08, 40, 57).

3. **A rejected entry is dropped for good, which can lose transcript data.**
   - `store.ts:534-540` drops every rejected entry.
   - `canEditDocument` is false for a trashed document, so segments pushed while the meeting note is in the trash
     come back `forbidden` and are deleted from the outbox.
   - After the note is restored, the server transcript has a permanent hole, and the local rows are never
     queued again.
   - Fix (either):
     - Keep `forbidden` or `not_found` entries for meeting children parked (an outbox `parked_at` column), and
       retry them when the parent changes or on a slow timer.
     - Let the document owner write meeting children even while the document is trashed (trash can be undone).

4. **A lost ack plus a later edit gives a false conflict** (flagged by the implementer). This is in
   `push.ts:300-304` and `store.ts:530-533`.
   - The client never learned version 1, so a later edit still carries `baseVersion` 0 and comes back as a
     `conflict`, and the user's latest text ends up in a spurious conflicted copy.
   - Proposed fix (client-only, no protocol change):
     - When a document entry is pushed, record a hash of the canonical content it sent (title plus
       `canonicalContent`) in a `doc_inflight(document_id, hash)` table. Clear it on `ok`.
     - On `conflict`, if the server row's hash matches any recorded hash, the server version is our own earlier
       write. Set local `version = server.version`, keep the outbox entry (it is pushed again on the new base)
       and don't create a conflicted copy.
   - Alternative (server): store `last_push_device` and `last_push_base` on the document. Treat a stale base as
     current when both equal the entry's device id and `baseVersion`.
   - Must land before the desktop edits documents (3.x).

5. **When a user gains access, the document's children are never sent.**
   - `pull.ts:63-86` sends only the rows whose change is in the page.
   - Say a teammate's private meeting note becomes `workspace` (the D-25 sharing path already exists). Members
     receive the document, but its meeting, participants and segments were emitted earlier as deletes (or
     dropped as orphans), and nothing sends them again. Members' desktops show the note without a transcript
     until a full re-pull.
   - Fix (3.5): when the server emits a document upsert, it can't tell whether the actor could read the row
     before. Either have the client backfill a document's subtree the first time it sees that document
     (`pull?document=<id>`), or have the server include the children of every meeting document in the page,
     bounded and paged.

Optional:
- `sync-engine.ts:263`: a 409 from *push* also resets the pull cursor. Limit this to pull.
- A cursor with very large digit runs passes `decodeCursor`, then `::xid8` fails with 22003, giving a 500 and
  endless backoff instead of 409. Range-check it in `pull.ts:51-57`.
- There is no per-row ordering for non-document tables. A delayed duplicate request (a timed-out push still
  running on the server) can overwrite a newer segment or meeting value (`ended_at`). A client-sequence guard
  in `setWhere` would prevent it.
- In team workspaces, pull sends `delete` tombstones with the ids of other members' private meetings and
  segments: metadata and volume (one per segment). Revisit in 3.5.
- A stale-cursor resync re-applies upserts but never sweeps local rows the server no longer has. Mark and sweep
