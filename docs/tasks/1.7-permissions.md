# 1.7 — `packages/core` domain types + permissions
status: done
milestone: M1 · deps: 1.1 · branch: task/1.7-permissions

## Goal
One place that decides who can do what (SPEC §6), as pure, exhaustively-tested functions, plus the shared
domain types every other package uses.

## Context
SPEC §4 (Sharing, Workspace), §6 (data model + read rule), FACTORY §3 (permission-sensitive code goes through
`packages/core/permissions.ts`, deny cases tested). Personal space = workspace with one member (no separate path).

## Scope
In:
- `packages/core/src/types.ts`: domain types/enums (zod schemas + inferred TS types) for Workspace,
  Membership/Role (`owner|admin|member|viewer`), Folder, Document (`kind`, `visibility: private|workspace|link`,
  `shareToken`, `deletedAt`), Meeting, Participant, TranscriptSegment (`source: mic|system`), Template,
  ChatThread/Message (minimal). IDs are strings. These are the contract `packages/db` (1.5) must match.
- `packages/core/src/permissions.ts`: pure functions taking an explicit context
  (`{ userId | null, memberships: Map<workspaceId, Role>, shareToken?: string }`) and the resource:
  `canReadDocument`, `canEditDocument`, `canDeleteDocument`, `canShareDocument` (change visibility/create link),
  `canReadFolder`, `canEditFolder`, `canManageMembers`, `canInvite(role)` (can't invite above own role),
  `canChangeRole`, `canRemoveMember` (last owner protection), `canDeleteWorkspace`, `canCreateInWorkspace`.
  Rules (write them down in a table in the file's doc comment and in Design notes):
  - owner of a document: full access. Soft-deleted docs: only owner/admin can read (for restore).
  - `workspace` visibility: members read; members+ edit; viewers read-only.
  - `private`: only the owner (admins do NOT see others' private docs).
  - `link`: anyone with a matching share token can read (read-only), plus workspace-visibility rules for members.
  - viewer can never edit/create. Personal workspace: cannot invite, cannot delete, single owner.
  - Folder `private` hides it from others; a document's own visibility is still checked.
- Return type: boolean helpers plus `assertCan(...)` throwing a typed `ForbiddenError` for API routes.
- Tests: table-driven, every rule incl. deny cases (anonymous user, wrong token, non-member, viewer edit,
  removed member, deleted doc, cross-workspace id spoofing). Aim for 100% branch coverage on permissions.ts
  (enable vitest coverage for this package and assert threshold).
Out: DB queries (callers load the data), auth (1.6).

## Acceptance criteria
- [ ] All rules above implemented and documented; every function has allow + deny tests.
- [ ] Coverage of permissions.ts ≥ 100% branches (or justified exceptions).
- [ ] Global gates green.

## Design notes
(implementer, 2026-11-14)

**Files.** `packages/core/src/types.ts` (zod schemas + inferred types + `readonly` enum tuples `ROLES`,
`WORKSPACE_KINDS`, `FOLDER_VISIBILITIES`, `DOCUMENT_VISIBILITIES`, `DOCUMENT_KINDS`, `TRANSCRIPT_SOURCES`,
`PARTICIPANT_SOURCES`, `CHAT_SCOPES`, `CHAT_MESSAGE_ROLES` for 1.5 to build/assert its pg enums from),
`packages/core/src/permissions.ts`, tests `permissions.test.ts` (table-driven, ~190 cases) and `types.test.ts`,
`src/index.ts` re-exports both. Deps: `zod ^4.6.7` (runtime), `@vitest/coverage-v8 ^5.1.0` (dev), both via catalog.

**Types contract (for 1.5).** camelCase fields ↔ snake_case columns. IDs = non-empty strings. Nullable columns
are `.nullable()` (always present), never optional. Timestamps are `Date` via `z.coerce.date()` (parses ISO
strings from JSON). Entities: User, Workspace, Membership, Invite, Folder, Document (`contentJson: unknown`
— shape owned by `@oat/editor`; `version` non-negative int; `shareToken` ≥ 22 base64url chars or null), Meeting,
Participant, TranscriptSegment (refine `endMs >= startMs`), Template (`sections: {heading, instructions}[]`
= SPEC `sections_json`), ChatThread (refine: `documentId` set iff `scope = document`), ChatMessage
(`parts: unknown[]`, owned by `@oat/ai`; roles `system|user|assistant`). Not modelled yet (not in scope):
enhancement, chunk, integration, audio_recording.

**Context.** `PermissionContext = { userId: string | null, memberships: ReadonlyMap<workspaceId, Role>,
shareToken?: string }`. `createPermissionContext({ userId, memberships: rows, shareToken })` builds it and drops
rows whose `userId` isn't the actor (and all rows for anonymous). `roleIn()` also returns `undefined` for
`userId: null`, so a malformed anonymous context with memberships grants nothing. Resources are structural
(`DocumentAccess`, `FolderAccess`, `WorkspaceAccess`, `MemberTarget`), so full entities fit.

**Rule table** (same as the doc comment in `permissions.ts`; rows evaluated top to bottom).
"Role" = actor's role in the *resource's* `workspaceId` (cross-workspace memberships never count).
"Doc owner" = `ownerId === userId` **and** still a member of that workspace. Editor role = owner|admin|member.

| Check | Rule |
|---|---|
| `canReadDocument` | trashed: doc owner, or workspace owner/admin if visibility ≠ private; tokens never work. Else doc owner → yes; `private` → no; `workspace` → any member (incl. viewer); `link` → any member, or anyone presenting a token equal to `shareToken` (constant-time compare; stored tokens < 22 chars (`MIN_SHARE_TOKEN_LENGTH`) never match). |
| `canEditDocument` | trashed → no. Non-member/viewer → no. Doc owner → yes. `private` → no. `workspace`/`link` → editor role. |
| `canDeleteDocument` (trash, restore, purge) | Non-member/viewer → no. Doc owner → yes. `private` → no. `workspace`/`link` → owner/admin. |
| `canShareDocument` (visibility, create/rotate link) | trashed → no. Non-member/viewer → no. Doc owner → yes. `private` → no. `workspace`/`link` → owner/admin. Entering `link` must issue a new token: `shouldRotateShareToken(from, to)` (D-18). |
| `decideMoveDocument(doc, target \| null)` → `MoveDecision`; `canMoveDocument` = its boolean `.allowed` (D-18) | target folder in another workspace → deny (no cross-workspace moves). Needs editor role in the workspace (create) **and** `canEditDocument`. Into root / a `workspace` folder → `{allowed: true}`. Into a `private` folder → only if actor owns the folder **and** the doc; returns `{allowed: true, setVisibility: 'private'}` unless already private (caller applies it in the same write). |
| `canReadFolder` | Non-member → no. Folder owner → yes. `private` → no. `workspace` → any member. |
| `canEditFolder` (rename) | Non-member/viewer → no. Folder owner → yes. `private` → no. `workspace` → editor role. |
| `canCreateInFolder` + `visibilityForNewItem(folder \| null, requested)` (D-18) | Same rule as `canEditFolder` (only the owner adds to a private folder). New items inside a private folder are always `private`; elsewhere the requested visibility is kept. |
| `canSetFolderVisibility(folder, to, containedOwnerIds)` (D-18) | `canEditFolder`, and making a non-private folder `private` additionally needs the actor to own the folder **and** every descendant doc/folder (`containedOwnerIds`, any other id → deny). Opening to `workspace` / no-op → edit rights suffice. |
| `canDeleteFolder` | Non-member/viewer → no. Folder owner → yes. `private` → no. `workspace` → owner/admin. |
| `decideMoveFolder(folder, target \| null, containedOwnerIds)` → `MoveDecision`; `canMoveFolder` = boolean (D-18) | Same as document move with `canEditFolder` on the moved folder. Into a private folder: own the target and the folder; if the folder isn't already private, also own every descendant (`containedOwnerIds`), and the folder becomes `private`. Moves to root/workspace folders ignore contents. Cycle prevention (target = itself/descendant) is the caller's job. |
| `canCreateInWorkspace` | editor role. |
| `canManageMembers` | team workspace and owner/admin. |
| `canInvite(role)` | manage members and `role ≤ actor role` (admin can invite admin/member/viewer, not owner). |
| `canChangeRole(target, newRole)` | manage members; `target.workspaceId` = workspace; owners change anyone; admins change only members/viewers (not other admins or themselves) and grant at most admin; never demote the last owner (`ownerCount ≤ 1`). |
| `canRemoveMember(target)` | team workspace; target in this workspace; never the last owner; actor must be a member. Self-removal (leave) → yes for any role. Otherwise owners remove anyone, admins only members/viewers. |
| `canDeleteWorkspace` | team workspace and owner. |

`assertCan(action, ctx, ...args)` dispatches through the frozen `permissions` name→check map (type-checked args
per action; names used because function names don't survive minification). It fails closed: throws unless
`Object.hasOwn(permissions, action)` and the check returns exactly `true` (so `constructor`, `toString`,
`__proto__`, typos from untyped input all throw). Moves return a decision, so they have
`assertCanMoveDocument` / `assertCanMoveFolder`, which return the allowed decision (with `setVisibility`) or
throw. `ForbiddenError` has `name`, `code: 'FORBIDDEN'`, `status: 403`, `action: string`; `isForbiddenError()`
for route handlers. Routes may choose 404 over 403 for unreadable docs to avoid leaking existence.

**Judgement calls.**
1. *Removed members lose ownership rights.* Ownership only counts while the owner is still a member of the
   doc's workspace; otherwise a removed member could keep reading/editing their old docs.
2. *Viewer caps everything, even on own resources.* "Viewer can never edit/create" → a doc owner demoted to
   viewer can still read their docs but not edit, delete or share them.
3. *Trashed private docs stay private.* "Only owner/admin can read deleted docs" vs "admins do NOT see others'
   private docs": privacy wins — admins can read/restore trashed docs only when visibility ≠ private.
   Trashed docs can't be edited or shared (restore first); share tokens stop working while trashed.
4. *Delete/share of others' docs needs admin.* Members can edit others' workspace/link docs but only doc owner
   or workspace owner/admin can delete/restore or change visibility/rotate the link. Same split for folders
   (`canDeleteFolder` added for symmetry; not in the original list).
5. *Token rotation (D-18).* The old `shareToken` may stay in the row when visibility leaves `link`, but it only
   opens a doc whose current visibility is `link`, and `shouldRotateShareToken` tells callers to issue a new one
   whenever a doc (re-)enters `link`, so turned-off links never revive. Schema + compare enforce ≥ 22 base64url
   chars; token generation itself belongs to the sharing task.
6. *Folder privacy (D-18).* Detail as implemented:
   - A private folder belongs to its owner: only they read it, rename it, add children or move things into it.
   - Invariant: everything inside a private folder is private and owned by the folder owner. Kept by
     (a) `visibilityForNewItem` forcing `private` for items created inside, (b) moves into a private folder
     requiring ownership of target + item and returning `setVisibility: 'private'`, (c) hiding a non-private
     folder (move into a private folder, or `canSetFolderVisibility(…, 'private', …)`) requiring ownership of
     the folder and every descendant (`containedOwnerIds`, loaded by the caller; empty = empty folder).
   - Reads stay non-cascading: each doc's own visibility decides. So a doc owner may still explicitly share a
     doc that lives in their private folder (deliberate, like sharing one page from a private section).
   - No cross-workspace moves in v1; cycle checks are the caller's.
   - Move results are objects, so they're named `decideMove*`; `canMove*` are strict booleans (also in the
     `assertCan` map), so `if (!canMoveDocument(...))` can't be fooled by a truthy object.
7. *Last-owner protection needs `ownerCount`* — passed in `MemberTarget`; its doc says routes must count owners
   under a row lock in the same transaction (TOCTOU). Re-asserting the last owner as owner is allowed (no-op).
   Only owners demote/remove admins (D-18); admins manage members/viewers and can promote up to admin
   (consistent with being able to invite admins), but can't undo that afterwards — an admin steps down by
   leaving or asking an owner.
8. *Personal workspace* (`kind: personal`): no member management, invites, role changes, removal/leaving or
   deletion; creating content and all doc rules work as normal (link sharing allowed).
9. *Constant-time token compare* is hand-rolled (pure, runs in browser/Electron/Node; no `node:crypto`).

**Notes for 1.5.** `Meeting.startedAt` is nullable (calendar notes before recording) though SPEC §6 doesn't
mark it `?` — make the column match. `share_token` should be unique and checked ≥ 22 base64url chars.

## Review
(reviewer, 2026-11-14) **Verdict: `changes`** — 2 findings. Read task file + `git diff main...task/1.7-permissions` only;
re-ran `pnpm --filter @oat/core test` (234 passed, permissions.ts 100% all metrics).

Checked and OK: private docs never visible to admins (incl. trashed); token only valid when `visibility = link`
and not trashed, length-independent loop compare, empty/null never match; every check derives the role from the
resource's own `workspaceId`, and `canChangeRole`/`canRemoveMember` reject `target.workspaceId ≠ workspace.id`;
viewer can never edit/create/delete/share (even own docs); invite/role escalation capped at actor's rank; last-owner
protection on demote/remove/leave; anonymous and spoofed-anonymous contexts grant nothing; personal workspace
locked down. zod types match SPEC §6. Tests are real deny-case tables, not coverage padding. Judgement calls
1–5, 7–9 are sensible conservative defaults.

1. **`assertCan` fails open on prototype keys** — `packages/core/src/permissions.ts:318-322`. `permissions` is a
   plain object, so an action that reaches it untyped (route param, JSON body, `as any`) resolves inherited
   members: verified `assertCan('constructor', anonCtx, {})` and `assertCan('toString', anonCtx, {})` **do not
   throw** (`Object(ctx)` / a string are truthy). Fix: `if (!Object.hasOwn(permissions, action) ||
   check(ctx, ...args) !== true) throw new ForbiddenError(action)` (or `Object.freeze(Object.assign(
   Object.create(null), {...}))`), and add a test that unknown/prototype action names throw.
2. **Judgement call 6 (folder privacy doesn't cascade) is the fail-open reading and will surprise users** —
   `permissions.ts:25-26, 195-213`, Design notes #6. In a Notion-like product, moving a page into "my private
   folder" means teammates can't see it; here a `workspace` doc in a private folder stays readable by every
   member, and the reverse also bites: a member may (via `canEditDocument` + `canEditFolder` on their own
   folder) move someone else's workspace doc into their private folder, hiding it from the doc owner's tree.
   `canEditFolder` ("add children") also never checks the child is in the same workspace, so nothing in core
   stops a doc in workspace A being filed into a folder in workspace B. Fix (keeps reads pure/non-cascading by
   making it an invariant): add `canMoveDocument(ctx, doc, target: FolderAccess | null)` (and the folder
   equivalent for `parentId`) requiring `target.workspaceId === doc.workspaceId`, `canEditDocument`,
   `canEditFolder(target)`, and, when `target.visibility = private`, that the actor owns the doc and the doc is
   (or is made) `private`; tests for each deny. Record the folder-privacy rule in `docs/DECISIONS.md` (or ask
   the human if you prefer true cascading).

Optional:
- Last-owner TOCTOU: `ownerCount` is caller-supplied; two owners demoting/leaving concurrently both see 2. Note in
  the `MemberTarget` doc that routes must count owners under a row lock in the same transaction (or a DB guard).
- Judgement 5: re-enabling `link` revives the old URL; consider rotating the token on re-enable (UX choice).
- `shareToken: z.string().min(1)` has no entropy floor; routes will look docs up by token in SQL (so the
  constant-time compare is moot there) — enforce a minimum length / single generator when 1.5/sharing lands.
- `Meeting.startedAt` is nullable though SPEC §6 doesn't mark it `?` — sensible (pre-recording calendar notes),
  but call it out for 1.5 so the column matches.
- Admins may demote/remove other admins (equal rank). Fine for v1; mention it in the member-management UI copy.
- Invite acceptance (email match, expiry, `acceptedAt`) has no core check yet; export the safe compare for
  invite tokens when that task comes.

### Re-review
(reviewer, 2026-11-14, `git diff 4dca132..task/1.7-permissions` vs findings 1–2 and D-18) **Verdict: `changes`** — 2 findings.
Tests re-run: 295 passed, permissions.ts 100%. Finding 1 fixed (`Object.hasOwn` + `!== true`, frozen map).
D-18 doc moves, no cross-workspace moves, token rotation (`shouldRotateShareToken`, ≥22-char tokens) and
"only owners manage admins" (`manages`) are correct and tested with deny cases.

1. **A folder can still hide other people's docs inside a private folder** (`permissions.ts:187-198`
   `decideMove` via `canMoveFolder`, and `canEditFolder` "change visibility"). `canMoveFolder` only checks
   that the actor owns the *folder*. A member who owns a workspace folder that teammates have filed docs into
   can nest it in their private folder (→ `setVisibility: 'private'`). They can also flip it to private
   directly through `canEditFolder`. Either way, teammates' docs end up under a folder they can't see. This
   is the D-18 case ("owning both") reached by moving a folder instead of a doc. Creating a doc/subfolder
   inside a private folder also never forces `private`. Fix: moving a non-private folder into a private folder
   and making a folder private require that every descendant is owned by the actor; take the subtree owner
   ids (e.g. `descendantOwnerIds`) or deny unless the folder is already private. Also give create-in-folder
   a decision that returns `setVisibility: 'private'` for private targets. Add deny tests.
2. **`canMoveDocument`/`canMoveFolder` return an always-truthy object** (`permissions.ts:253-259, 293-299`),
   unlike every other `can*`. A route written `if (!canMoveDocument(ctx, doc, f)) throw …` never throws, and
   ESLint here has no `strict-boolean-expressions`/type-checked rules to catch it. Fix: rename them to
   `decideMoveDocument`/`decideMoveFolder` (keep `assertCanMove*`), or make `canMove*` return `boolean` with a
   separate `moveVisibility()`.

Optional: an owner can share a doc that lives in their private folder back to `workspace` (fine as explicit
intent), after which a member may move it out of that folder (no source-folder check). Acceptable for v1.
