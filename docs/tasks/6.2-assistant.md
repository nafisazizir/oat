status: done

## Goal
A grounded assistant: chat scoped to one note or the whole workspace, answering from transcripts and notes via
tools, every factual claim citing segments/blocks, streaming, with threads persisted.

## Context

`packages/ai` reusable by eve later), D-20, `@oat/ai` (getModel('chat'), buildMeetingContext + MEETING_CONTEXT_RULES

enhance-chat.md` (behaviour reference only). Load `vercel:ai-sdk` skill for current tool-loop APIs.

## Scope
In:
- Tools in `@oat/ai/tools` (pure functions taking a permission context + db): `searchMeetings(query, filters)`
  → chunk hits with refs; `getDocument(id)` → Markdown with block ids; `getTranscript(meetingId, range?)` →
  segments with ids + start_ms; `listMeetings(filter: date range, attendee, folder)`; `updateDocument`
  (find/replace → minimal block diff) returning a *pending* proposal that requires user approval (never writes
  directly). Every tool re-checks permissions; results fenced as data.
- Chat API: `POST /api/chat` (AI SDK UI message stream) with `{threadId?, scope: {kind:'document', documentId}
  | {kind:'workspace', workspaceId}, messages}`; system prompt (ours) with grounding rules: cite with
  `[[seg:<id>]]`/`[[block:<id>]]` markers only for ids returned by tools (server validates citations against
  tool results and strips unknown ones); step limit; token caps; persists thread + messages (`parts_json`,
  `context_json`); `GET /api/chat/threads`, `GET /api/chat/threads/:id`; approval endpoint for
  updateDocument proposals → applies via documents API with baseVersion.
- Mock support: the dev mock LLM must exercise a tool call path (e.g. scripted: first call → searchMeetings,
  second → answer with citations from tool output) so e2e works offline.
- Evals (6.5 groundwork): add a `chat` suite to the eval harness with 3 fixture Q&As (citation validity +
  must-mention), structural tier offline.
- Tests: tool unit/int (permission deny cases incl. other user's private doc via search/get), citation
  validation, approval flow (stale baseVersion → 409), API int (authz, coverage markers), streaming smoke.

## Design notes

**Layout.** `@oat/ai/tools` (new subpath export, `packages/ai/src/tools/`) and `@oat/ai/chat` (`src/chat/`);
nothing added to the `@oat/ai` barrel (4.4 works there). HTTP layer: `apps/web/src/server/chat.ts` +
`src/app/api/chat/**` route files, wire types in `src/lib/chat-types.ts`.

**Tools = plain functions over a data port** (`src/tools/tools.ts`). Signature `(ctx: ToolContext, input)` with
`ToolContext = { permissions, data: AssistantData, scope, onProposal? }`. Deviation from "permission context + db":
the tools take an `AssistantData` port instead of `Db` so the same functions run against Postgres
(`createDbAssistantData(db, { search })`) and in memory (`createMemoryAssistantData`, used by evals and unit tests —
no database offline). `search` is injected because `@oat/indexing` depends on `@oat/ai` (no cycle); the web app
passes `searchChunks`. `@oat/ai` now depends on `@oat/db` + `drizzle-orm` (for the db adapter only).
- **Permissions:** every row the port returns is re-checked in the tool with `@oat/core` `canReadDocument` /
  `canEditDocument`, using the actor *without* a share token (a link never widens chat), trashed docs excluded, and
  the chat scope enforced (workspace chat = that workspace only; document chat = that document only). Out-of-scope
  and unreadable look identical (`{ error: 'not_found' }`) so the model can't probe ids. A misbehaving index is
  covered by a test (search returning a private doc → dropped).
- **Fencing:** user content goes out tag-neutralised (`neutralizeTags`) inside `<oat:excerpt|document|transcript>`
  blocks, and `[[`/`]]` in content are defused with a zero-width space, so content can neither close a fence nor
  forge a citation marker. The system prompt extends `MEETING_CONTEXT_RULES` to tool results.
- **Outputs carry the exact marker to cite:** search excerpts `{ cite: '[[seg:<id>]]', at, speaker, text }` per
  segment / per note block (the tool resolves chunk refs back to live segments/blocks, dropping refs whose segment
  no longer belongs to that document's meeting); `getTranscript` lines start with `[[seg:<id>]]`; `getDocument` is
  Markdown with `<!-- id=… -->` annotations (cite as `[[block:<id>]]`). `listMeetings` (workspace chats only):
  date range on `coalesce(started_at, document.created_at)`, attendee ILIKE on participant name/email, folder.
- **updateDocument** never writes. `applyTextEdits` (`src/tools/edit.ts`): each `find` must match exactly once over
  text blocks (any block with an id and inline-only children); only the touched inline nodes change (marks of the
  surrounding text kept, replacement takes the marks where the match starts, mentions can't be matched through,
  block ids/origins kept). The tool returns `{ proposalId, status: 'pending', baseVersion, changes[] }` and reports
  the proposal to `onProposal`.
- Caps (`TOOL_LIMITS`): ≤12 search results × ≤6 excerpts of ≤600 chars; documents ≤12k tokens; transcripts ≤300
  segments / ≤10k tokens per call with `nextFromMs` paging; ≤50 meetings.

**Citations** (`src/chat/citations.ts`). `CitationRegistry` collects allowed ids by scanning *every string* in tool
outputs for `[[seg|block:…]]` markers and `<!-- id=… -->` annotations (shape-agnostic, so new tools need no
registry code); history tool outputs (server-persisted parts) are registered too, and a document chat registers its
context's block ids plus transcript refs (`s12` → segment id). `CitationFilter` runs as `streamText`
`experimental_transform`: it registers ids on `tool-result` parts and rewrites `text-delta`s, holding back a partial
`[[…` (max 200 chars, no newline) until it closes; known markers are normalised (`[[seg:s12]]` → real id), unknown
or malformed ones (`[[seg: x]]`, wrong kind) are stripped, other `[[…]]` text passes. Because it is a stream
transform, the client stream, `result.text` and the persisted parts all see the filtered text. Kept/dropped
markers go to `context_json`.

**Turn** (`src/chat/run.ts` `streamAssistant`): `streamText` with our instructions (`src/chat/prompt.ts`, written
for Oat: grounding + cite-as-you-go + no invented ids + edits are proposals + data rules + today's date),
`convertToModelMessages(history, { tools })`, `stopWhen: isStepCount(6)`, `maxOutputTokens: 2000`. History is
trimmed to the newest 24 messages / ~24k tokens starting on a user turn; user messages ≤8000 chars. Document chats
load the note via `loadDocumentContext` → D-20 `buildMeetingContext` (transcript ≤24k tokens, notes ≤8k) appended
to the instructions.

**API** (`apps/web/src/server/chat.ts`, all via `apiRoute`: CSRF guard, session, actor):
- `POST /api/chat` `{ threadId?, scope, messages, timeZone? }` → `result.toUIMessageStreamResponse`. Only the
  **last** client message is used (must be a user text message); history is loaded from the thread, so a client
  can't inject fake tool results or citations into the context. Scope check: document must be live + readable
  (404), workspace needs membership (404); an existing thread must be the actor's (404) and match the scope (400).
  The user message is stored before streaming; the assistant message (id generated server-side via
  `generateMessageId`) is stored in `onEnd` (with `consumeSseStream: consumeStream`, so an aborted client still
  gets the partial answer saved) with `context_json = { scope, citations, dropped, proposals, toolCalls,
  finishReason, aborted?, model }`. Thread id: response header `x-oat-thread-id` and `start` message metadata
  `{ threadId, userMessageId }`. Thread title = first question (80 chars). `request.signal` aborts the model.
- `GET /api/chat/threads?workspaceId&documentId?` and `GET /api/chat/threads/:id`: threads are private to their
  creator; visible only while the creator is still a workspace member and (note chats) the note is still live and
  readable. Messages come back as UI messages with metadata `{ threadId, citations, proposals }` (assistant).
  Tool outputs inside earlier answers stay as they were shown at the time.
- `POST /api/chat/threads/:id/proposals/:proposalId` `{ decision: 'approve'|'reject' }`: locks the message row
  carrying the proposal (`FOR UPDATE`, so double clicks serialise), refuses decided ones (409 `proposal_closed`,
  new `ApiErrorCode`), then for approve re-reads the document through `getDocument` (404 if no longer readable),
  checks `version === baseVersion` (else status `stale` + 409 `stale_version` with the server copy), re-applies
  the stored edits to the current content and writes through the documents API `updateDocument` (edit permission,
  D-19 `baseVersion` guard, content validation; a lost race → `stale` + 409). Status is saved as
  `applied` (+ `appliedVersion`) / `rejected` / `stale` / `failed`. Proposals are stored in the assistant message's
  `context_json.proposals` (edits + changes + baseVersion, not a content snapshot) — no migration.
- All four routes have `denies(...)` markers in `src/server/api/chat.int.test.ts`.

**Mock LLM** (`tools/mocks/src/providers/llm/tools.ts`): with `tools` offered and no tool result since the last
user message it returns a tool call — `mock:tool <name> <json>` as the user message calls exactly that tool
(exercises `updateDocument` offline), else a forced `tool_choice`, else the first tool with a string `query`
param (search) with the user message as query; streaming sends the call as one `tool_calls` delta and
`finish_reason: tool_calls`. Once results are in it answers with the first sentence of up to three `{ cite, text }`
items found in the tool JSON, each followed by its `cite`. `@oat/ai/chat/testing` `createMockChatModel()` runs that
provider in-process through the real OpenAI-compatible provider (custom `fetch` → Hono `app.request`), used by
unit tests, evals and the web int tests. The compose `mocks` container gets it after `pnpm dev:build` on main.

**Evals** (`src/evals/chat-suite.ts`, fixtures `evals/chat/fixtures.ts`, synthetic): 3 questions over one team
workspace (2 workspace chats, 1 note chat) with a teammate's private note as a leak trap. Structural: answered,
cited, every citation resolves to a segment/block the asker can read. Property: must-mention, must-not-mention
(leaks / other meetings in a note chat), cites an expected source. Mock baseline recorded (all 1.0). The existing
real-mode CLI tests now pass `--suite enhance` (the fake models there only speak enhance).

**Touched outside the listed paths:** `apps/web/src/lib/api-types.ts` (`proposal_closed` error code),
`docs/DEV.md` (mock LLM tool loop + `createMockChatModel`), `packages/ai/src/evals/cli.test.ts` (scope real-mode
tests to `--suite enhance`), `packages/ai/evals/index.ts` + `baseline.json` (register the chat suite). No migration.

**Review 1 fixes** (after merging main 124ba07, 4.4 enhance):
1. Citation filter: a `[[…]]` span that isn't marker-shaped now lets only its first `[` through and rescans from
   the next character, so markers nested in it are checked (`[[[seg:fake]]` → `[`, `see [[note [[seg:fake]] x` →
   `see [[note  x`, `[[\n[[seg:fake]]` → `[[\n`); tests run each case through every chunk size 1–5.
2. Allowed block ids are no longer read from `<!-- id=… -->` text. `getDocument` returns a structured
   `blockIds` array (the registry trusts string arrays under that key only; object keys never come from user
   content); `defuse` now also neutralises `<!--` (ZWSP), and `getDocument` defuses `<!--` in the TipTap text
   *before* serialising, so only the serializer's own annotations appear in its Markdown. Test: typed, inline-code,
   code-block and transcript `<!-- id=victim -->` never become citable.
3. Aborted turns: history goes through `convertToModelMessages(…, { ignoreIncompleteToolCalls: true })`, and
   `completeParts` drops tool parts without a final state before the answer is saved. Tests (unit + int, both
   fail with `MissingToolResultsError` without the fix): a thread with an unfinished tool call answers the next
   turn.
4. `POST /api/chat` is rate limited per user (`CHAT_RATE_LIMITS`: 20/min, 500/day, keys `chat:minute|day:<user>`)
   through the shared API limiter (`apiRateLimiter()` exported from `src/server/api/index.ts`, Redis in prod;
   routes now use `src/server/chat-api.ts`): 429 `rate_limited` + `retryAfter`. Int test (limited user refused,
   others unaffected).
- Optional, done: the proposal approval reads and writes the document inside the transaction that locks the

**For a D-entry (orchestrator):** earlier tool outputs stay in a thread's history after the user loses access to a

## Review

**Review 1 (2026-11-14, fresh reviewer, security + grounding focus): `changes`.**

Checked and fine: every tool row re-checked with `@oat/core` (actor without share token, trash excluded, scope enforced,
out-of-scope == not_found); `listMeetings` SQL mirrors `searchChunks` (member, live doc + workspace, owner or not
private) and is re-filtered; document scope can't reach other docs (search/get/transcript/update all go through
`canSee`); threads are owner-only and re-check membership + note readability; server ignores client history;
proposals are owner-only, scope-checked at creation, re-applied at `baseVersion` through the documents API (edit
permission + D-19 guard), `FOR UPDATE` serialises double clicks; fencing defuses `<oat:` and `[[`/`]]`.

1. **Citation filter bypass** — `packages/ai/src/chat/citations.ts:124-135`. When the span from the first `[[` to
   the next `]]` is not a marker, `#marker` returns the whole span unchanged, so a fake marker nested inside it
   survives. Verified: `[[[seg:fake]]`, `see [[note [[seg:fake]] x`, `[[\n[[seg:fake]]` all pass through and
   `extractCitations` reports `seg:fake`. Fix: if the span isn't `LOOSE_MARKER`, emit only the leading `[` (or
   everything up to the last `[[` inside the span) and keep scanning; add these cases to `citations.test.ts`.
2. **User content can whitelist block ids** — `citations.ts:28,50`. `BLOCK_ANNOTATION` is matched in *every*
   tool-output string, and user text isn't defused for it: `toMarkdown` turns a typed `<!-- id=victim -->` into
   `\<!-- id=victim -->`, which still matches (also raw in transcript/excerpt text). Fix: neutralise `<!--` in
   `defuse`, or anchor the regex (not preceded by `\`, at end of line), or have `getDocument` return block ids
   as a structured field the registry reads.
3. **An aborted turn bricks the thread** — `packages/ai/src/chat/run.ts:172`. `onEnd` persists aborted answers
   (`apps/web/src/server/chat.ts:365`); if the abort lands during a tool call the stored part is
   `input-available`, and every later turn's `convertToModelMessages(history, { tools })` yields a tool call with
   no result → `MissingToolResultsError` (ai@7.0.173 `convertToLanguageModelPrompt`) → 500, after another user
   row is inserted. Fix: `ignoreIncompleteToolCalls: true` (and/or drop non-final tool parts before persisting);
   add a test with an aborted tool part in history.
4. **No per-user rate limit on `POST /api/chat`** — `apps/web/src/server/chat.ts:486`. The most expensive route
   (≤6 steps × ~24k history + ~32k note context + tool outputs up to 12k each) has no limiter, though
   `apiDeps.rateLimiter` (Redis) already exists and `notion.ts:113` uses it. Any member (viewers included) can
   loop it. Fix: `rateLimiter.hit('chat:<userId>', …)` → 429 `rate_limited` with `retryAfter`, plus an int test.

Optional:
- `decideProposal` reads/writes via `db`, not `tx` (`chat.ts:431,442`): the document write commits independently
  of the proposal status; a failed status save leaves it `pending` (re-approve then goes `stale`, so safe). Note it.
- Earlier tool outputs stay in history after a document becomes unreadable: re-sent to the model, re-registered as
  citable, returned by `GET /threads/:id`. Fine as "what you were shown", but write it down as a decision.
- 6.4: the proposal `summary` is model-written (injection can mislabel a change) — show the document title and
  the before/after diff, not just the summary; render `changes` as plain text.
- `memory.ts:146` uses `doc.updatedAt` where SQL uses `document.created_at` for undated meetings.
