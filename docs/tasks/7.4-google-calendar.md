# 7.4 — Google Calendar (OAuth + events API, mocked in dev)
status: done
milestone: M7 · deps: 1.6, 7.1 · branch: task/7.4-google-calendar

## Goal
Users without macOS Calendar (and the web app) get upcoming meetings from Google Calendar, normalised into the
same `CalendarEvent` (7.1). Dev/tests run against a Google Calendar API subset in `tools/mocks` (D-11).

## Context
D-11, D-21, `@oat/core` CalendarEvent + helpers, `@oat/calendar` (CalendarSource, CalendarCache),
`@oat/auth` (Google via genericOAuth pointed at OAUTH_GOOGLE_ISSUER; account linking rules), `tools/mocks`
(provider structure, `startMocks()`), `docker/oauth` mock config, SPEC §6 `integration` table.

## Scope
In:
- OAuth: request calendar read scope (`https://www.googleapis.com/auth/calendar.readonly`) as an incremental
  "Connect Google Calendar" flow (separate from sign-in, so sign-in scopes stay minimal); store tokens in
  Better Auth `account` (encrypted at rest if Better Auth supports it; else note) with refresh handling.
  Mock OAuth issues tokens with the requested scope.
- `tools/mocks` `gcal` provider: `GET /gcal/calendar/v3/users/me/calendarList`, `GET
  /gcal/calendar/v3/calendars/{id}/events` (timeMin/timeMax/singleEvents/orderBy/pageToken/syncToken subset,
  conferenceData, attendees with responseStatus/self/organizer), bearer validation against the mock OAuth
  token (or accept any non-empty bearer in dev — document), fixture data derived from
  `fixtures/calendar/week.json`; 410 on stale syncToken.
- `@oat/calendar` `GoogleCalendarSource` (server-side, Node): base URL from env (`GOOGLE_CALENDAR_BASE_URL`,
  default the mock), pagination, incremental sync tokens with 410 → full resync, normaliser → CalendarEvent
  (conference links from conferenceData/hangoutLink/location/description via shared detector), per-user cache.
- `apps/web`: `/settings/integrations` "Connect Google Calendar" + disconnect; `GET /api/calendar/upcoming`
  (session-auth) merging connected sources; Home shows "Upcoming" list (next 5, with join link + "Start
  notes" placeholder action).
- Tests: normaliser unit tests, mocks tests, int tests (connect flow against mock OAuth + gcal mock, 410
  resync), web e2e: connect → upcoming list renders fixture events. Screenshots.
Out: writing to calendars, push notifications/webhooks, desktop wiring (desktop uses EventKit + this API).

## Design notes
(implementer, 2026-11-14)

**Shape.**
```
browser ──link-social(google-calendar)──► Better Auth ──OAuth (calendar.readonly, offline)──► issuer (mock :18089 / Google)
                                             │ account row providerId=google-calendar (tokens AES-encrypted)
Home / GET /api/calendar/upcoming ─► server/calendar.ts ─► GoogleCalendarSource (per account, in memory)
                                             │ token: auth.api.getAccessToken / refreshToken
                                             └─► GoogleCalendarClient ──► ${GOOGLE_CALENDAR_BASE_URL}/calendar/v3/…
                                                                          (mock ${MOCKS_URL}/gcal | www.googleapis.com)
```

**OAuth: a link-only second provider, not incremental scopes on `google`.** `@oat/auth` gets a second
`genericOAuth` entry, `google-calendar` (same issuer discovery + client, scopes `openid email profile
calendar.readonly`, `accessType: offline`, `prompt: consent`, PKCE, id_token verified, `disableSignUp`).
The UI starts it with Better Auth's `POST /api/auth/link-social { provider: 'google-calendar' }` (signed-in
session required; callback `/api/auth/callback/google-calendar`). Why not add the scope to the `google`
account: a later Google sign-in overwrites that row's tokens with sign-in-scoped ones (and real Google only
re-issues a refresh token with `prompt=consent`), silently killing calendar access. A separate row
(`account_provider_account_uq` is per provider) keeps sign-in minimal and calendar tokens stable; the int test
proves a later sign-in leaves the calendar row untouched. `hooks.before` refuses `/sign-in/social` with
`google-calendar`, so the grant can never become a login method. Better Auth's linking rules apply: the Google
account's verified email must equal the user's (`?error=email_does_not_match` otherwise, with our copy in
`lib/calendar-errors.ts`; follow-up below).
- **Encrypted at rest:** `account.encryptOAuthTokens: true` (Better Auth symmetric encryption with the auth
  secret; applies to all OAuth accounts; existing plaintext rows still decrypt — it checks the format). The
  int test asserts the column isn't the JWT. id_tokens stay plain (Better Auth's choice; we read the email
  from it for display).
- **Refresh:** `googleCalendarTokenProvider(auth.api, { accountId, userId })` → `auth.api.getAccessToken`
  (Better Auth refreshes + persists when the token expires within 5 s) or, on `forceRefresh`, `refreshToken`.
  The Calendar client asks for a forced refresh once on a 401 and retries.
- **Scope bookkeeping:** the mock issuer (navikt 7.0.0) returns no `scope` on the code exchange and can't
  template it into a claim (tried `"scope": "${scope}"` in a throwaway container: emitted literally), so
  `docker/oauth` is unchanged. Per RFC 6749 §5.1 an omitted scope means "as requested": a
  `databaseHooks.account.create.before` fills `scope` with the requested calendar scopes for
  `google-calendar` rows only when the response had none (real Google always sends it, so it's a no-op there).
  `GoogleCalendarConnection.hasCalendarScope` is false if the user unticked calendar on Google's granular
  consent → "Connect again" in settings, "Reconnect" on Home.
- **Disconnect** (`disconnectGoogleCalendar`): best-effort RFC 7009 revoke at the discovered
  `revocation_endpoint` (Google revokes the whole grant; mock returns 200), then delete the `google-calendar`
  row. Better Auth's `unlink-account` isn't used: it refuses to remove a magic-link user's only account.

**`tools/mocks` `gcal` provider** (`src/providers/gcal/`): `fixture.ts` converts `week.json` (EventKit
shape) to Google v3 resources — calendarList entries (first = primary, lower-case hex colours), timed events
as `dateTime` with the zone's offset + `timeZone`, all-day as exclusive `date`s (EventKit's 23:59:59 end → next
day), recurring occurrences as `singleEvents` instances (`<series>_<YYYYMMDDTHHMMSSZ>`, `recurringEventId`,
`originalStartTime`), organizer always in `attendees` with `organizer: true` (as Google does), rooms as
`resource: true`, fixture `url` → `source.url` plus Meet `hangoutLink`/`conferenceData` or Zoom/Teams add-on
`conferenceData`, `externalId` → `iCalUID` (else `<id>@google.com`), cancelled = deleted. `index.ts` serves
calendarList + events list (timeMin/timeMax overlap, `singleEvents=true` required — documented mock
limitation, `orderBy`, `showDeleted`, `maxResults`/`pageToken` bound to the query, `syncToken` with deltas
incl. deletions, 410 `fullSyncRequired` for stale/foreign/garbage tokens or after
`POST /_mock/expire-sync-tokens`), get/insert/patch/delete for tests, Google-style error bodies. **Auth:** any
non-empty bearer (documented), but 401 for an expired JWT or a token revoked via `POST /_mock/revoke-token`,
403 `insufficientPermissions` for a JWT whose `scope` lacks calendar. **Dates:** `anchor: 'next-week'`
(default) shifts the fixture by whole weeks of wall-clock time per event zone so its Monday is the first one
after now (always upcoming; deterministic list for e2e); `'fixture'` (or `GCAL_MOCK_ANCHOR=fixture`) keeps the
real dates. A week change rebuilds state with a new epoch (old sync tokens → 410). Dockerfile copies
`week.json`; turbo inputs include it.

**`@oat/calendar/google`** (new export; fetch + zod only, so server/desktop-main safe):
- `normalize.ts` `normalizeGoogleEvent(event, calendarInfo)` mirrors the Swift normaliser rules: ids
  `google:<calendarId>/<eventId>`, `recurrenceId` from `recurringEventId` (or a master's own id), all-day =
  midnights in the calendar zone, timed zone = event's else calendar's, `url` = `source.url`, join link from
  `conferenceData` video entry → `hangoutLink` → `detectConferenceLink(url, location, description)` (the shared
  `@oat/core` detector; unknown products fall through), attendees (resources dropped, lower-cased, de-duped,
  `needsAction`→`needs_action`, organizer flagged or prepended as accepted when there are attendees but not
  for solo events; calendar addresses never prepended), schema-validated (null for deleted stubs, bad dates,
  unknown zones). `calendarInfoFromListEntry` (summaryOverride, upper-cased colour).
- **Parity test** (acceptance): `fixtures/calendar/week.eventkit.jsonl` is the golden EventKit output
  (`oat-audio calendar events --fixture week.json --from 2026-11-15T00:00:00Z --to 2026-11-23T00:00:00Z`, 17
  events). `normalize.test.ts` runs the same fixture through the mock's Google conversion + the Google
  normaliser and asserts every field equal except the source-specific `id`/`source`/`recurrenceId` (same
  series grouping asserted separately) and `icalUid` where EventKit has none (Google always has one). The
  sidecar int test asserts the live binary still prints the golden file, so the two can't drift.
- `client.ts` `GoogleCalendarClient`: calendarList + events with full pagination (`singleEvents=true`,
  `maxResults` 250), 15 s timeout, 401 → forced token refresh + one retry, errors → `GoogleCalendarApiError` /
  `GoogleCalendarAuthError` (401 after refresh, 403 insufficientPermissions/forbidden, token provider failure)
  / `GoogleSyncTokenExpiredError` (410).
- `source.ts` `GoogleCalendarSource implements CalendarSource` (one instance per connected account = the
  per-user cache): full sync (readable calendars = primary or `selected`, not hidden/deleted/free-busy;
  window now −1 d … +28 d, widened to the requested range) keeps each calendar's `nextSyncToken`; later reads
  (≥ `minSyncIntervalMs`, default 30 s) re-list calendars and pull deltas per calendar (upsert / remove
  cancelled; renamed calendar → refs updated); 410 → that calendar fully re-synced; a range outside the
  window or 24 h since the last full sync → full sync. Concurrent reads share one sync. Auth errors clear the
  cache, `status()` → `denied`, reads throw `CalendarAccessError` (so `CalendarCache` behaves as with EventKit
  without access); next good sync recovers. Cancelled events are not shown (Google can't distinguish
  "organizer cancelled" from "deleted"; EventKit shows them as `cancelled`, which the core helpers filter out
  anyway). `watch` polls (default 60 s) — push notifications are out of scope.
- `config.ts` `resolveGoogleCalendarBaseUrl(env)`: `GOOGLE_CALENDAR_BASE_URL` → `https://www.googleapis.com`
  if `OAUTH_GOOGLE_ISSUER` is accounts.google.com → `${MOCKS_URL}/gcal` → (production: throw) →
  `localhost:14010/gcal`. So real Google is env-only, and dev/test never reach Google.
- `merge.ts` `mergeCalendarEvents(lists)` (main entry): one copy per iCalUID + start, first source wins, sorted.

## Review

### Review 1 (reviewer, 2026-11-14) — verdict: **changes**
Read: task file + `git diff main...task/7.4-google-calendar`, plus Better Auth 1.7.25 internals the design relies on
(`generic-oauth`, `api/routes/{callback,account}.mjs`, `oauth2/{link-account,utils}.mjs`, `crypto`).

Checked and fine: state + PKCE + per-provider redirect URI; `/sign-in/social` refused for `google-calendar` (generic
providers are registered as social providers in 1.7, so there is no separate `/sign-in/oauth2` path) +
`disableSignUp`; link callback enforces live session, verified email, email match (`allowDifferentEmails` unset) and
"already linked to a different user" server-side; tokens encrypted with XChaCha20-Poly1305 (AEAD, key =
SHA-256(secret)), refreshed tokens re-encrypted, old refresh token kept when Google omits it; no tokens in API
responses, page props or log lines; `/api/calendar/upcoming` keyed only by the session user's own `account` row;
410 → per-calendar full resync; revoke-then-delete is idempotent; proxy matcher `/settings/:path*` also matches
`/settings` and nothing public; mock 410/paging/sync semantics match Google's documented behaviour.

1. **Scope hook can record scopes that were never granted** — `packages/auth/src/server.ts:125-133`. Besides the
   code exchange, Better Auth's `POST /link-social` accepts `{ provider: 'google-calendar', idToken: { token, nonce,
   accessToken, refreshToken } }` (the provider has an `idToken` config because of `requireIdTokenVerification`);
   that path creates the row with **no** `scope` and caller-supplied tokens, and the hook then stamps
   `calendar.readonly` on it. Self-only impact, but it is exactly the "records scopes not granted" case. Fix: in
   `hooks.before` also refuse `/link-social` when `provider === google-calendar && body.idToken`; and gate the
   scope fill to the mock issuer (`new URL(config.google.issuer).hostname !== 'accounts.google.com'`) so it is
   provably a no-op with real Google. Add an int test for the idToken-link refusal.
2. **`?days≈28` forces a full sync on every request** — `apps/web/src/app/api/calendar/upcoming/route.ts:10` with
   `packages/calendar/src/google/source.ts:192-198,217-220`. The synced window ends at `syncNow + 28 d`; a request
   at a later `now` with `days=28` asks for `now + 28 d` > `window.to`, so `covered` is false and `#full` runs
   (calendarList + every calendar) on every call, bypassing `minSyncIntervalMs`. Any signed-in user (or a future
   desktop poller) can burn the shared project's Calendar API quota. Fix: cap `days` well under the window (e.g.
   `max(21)`), or pad the window (`to = max(now + futureMs, range.to + 1 d)`) so successive reads stay covered; add a
   source test that two reads with the max range do one full sync.
3. **Google "working location" events become meetings** — `packages/calendar/src/google/api.ts:37-62`,
   `normalize.ts:142`. `events.list` returns every `eventType` when unset; timed `workingLocation` blocks ("Office
   9–13", "Home 13–17") are timed, attended-by-default, and pass `upcoming()`, so they show on Home (and would name
   meetings under D-21 once desktop uses this API). EventKit doesn't surface them, so this also breaks parity.
   Fix: add `eventType` to `GoogleEventSchema`, return null for `workingLocation` (consider `birthday` too), unit
   test + one mock fixture event.

Optional:
- `server.ts:90` comment says "AES" — it is XChaCha20-Poly1305. Document the rotation story in DEV.md: rotate via
  `BETTER_AUTH_SECRETS` (versioned, keep the old one); changing `BETTER_AUTH_SECRET` alone makes stored tokens
  undecryptable (degrades to "Reconnect", sessions also reset).
- Better Auth's `/get-access-token` and `/account-info` hand the signed-in user their plaintext calendar tokens; add
  them to `disabledPaths` if "tokens never reach the client" is meant literally (server uses `auth.api` directly).
- Revoking the calendar token revokes the whole Google grant for the shared client (sign-in tokens too). Harmless
  today; worth a comment in `disconnectGoogleCalendar`.
- Re-link merges scopes (`mergeScopes`), so "Connect again" with calendar unticked keeps the old calendar scope →
  Integrations says Connected while Home says Reconnect (403). Already partly in follow-ups.
- `#full`/`#incremental` use `Promise.all`: one calendar's 404/5xx hides all events, and a 403 `forbidden` on a
  single shared calendar clears the cache and asks to reconnect. Consider per-calendar failure isolation.
- `sync()` coalescing hands a concurrent wider-range caller the narrower window's result.
