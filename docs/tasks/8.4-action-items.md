# 8.4 — Action items: extraction, checklist blocks, "My tasks"
status: done
milestone: M8 · deps: 4.4 · branch: task/8.4-action-items

## Goal
Every meeting's commitments become trackable: enhancement already emits `task` blocks (with optional
owner/due — 4.2 schema); make them first-class action items with an owner, due date and done state, and give
each user a "My tasks" view across meetings.

## Context
SPEC §4 (Integrations: action items), §7, D-20, D-26, `@oat/ai` enhance schema (task blocks with owner/due),
`@oat/editor` (taskItem node; add attrs `owner` {name, email?, userId?} and `due` ISO date — schema change:
attrs are additive; validateDoc + markdown round-trip must handle them), `@oat/db` (new `action_item` table
derived from documents — or a query over content_json? decide: a derived table maintained on document write /
by the change_log worker (D-22) is better for querying), `@oat/core` permissions (only items in docs the user
can read; "assigned to me" matches owner userId or email), `apps/web`.

## Scope
In:
- Editor: task items show owner chip + due date; inline edit (assign to a workspace member via mention-like
  picker; date picker); `@oat/editor/markdown` emits `- [ ] Text (@Owner, due 2026-11-20)`; Notion converter
  maps owner/due into text.
- Enhance: map schema `task.owner/due` → taskItem attrs; resolve owner names to workspace members/attendees by
  name/email match (exact or unambiguous fuzzy), else keep the name text.

  soon/overdue), grouped by meeting; toggling done updates the source document (baseVersion, 409 handling);
  links jump to the block (`?block=`). Sidebar + ⌘K entries.
- Tests: editor attrs + markdown round-trip, enhance mapping, worker extraction (int), API authz (deny markers),
  e2e (enhance mock meeting → tasks appear in /tasks → toggle done → document updated). Screenshots.
Out: pushing tasks to Linear etc. (IDEAS), reminders/notifications.

## Design notes

**Decision (proposed D-29, for the orchestrator to log — DECISIONS.md is outside this branch's scope):**
action items are a *derived* table `action_item`, never canonical (D-4: the TipTap body is). It is written by
the index worker per `document:<id>` job (D-22 change_log follower; `syncActionItems` runs *before* the
embedding work, so "My tasks" never waits on — or breaks with — the embedding provider) and by the toggle API
right after it writes the note (write-through, so the list is current immediately). A per-document advisory
lock + `document_version` guard means an older extraction never overwrites a newer one. Querying JSON in
`content_json` was rejected: "assigned to me across every workspace, filtered by due date" needs indexes.

**Schema (editor, additive).** `taskItem` gains `owner: { name, email?, userId? } | null` and
`due: 'YYYY-MM-DD' | null` (a calendar day, no time zone — "due Friday" is Friday everywhere). `validateDoc`
refuses unknown owner keys, multi-line/empty names, bad emails, impossible dates. Neither attr survives Enter
(`keepOnSplit: false`). HTML: `data-owner` (JSON) + `data-due` on the `<li>` for copy-paste, plus a read-only
`<span data-task-meta>@Name, due 2026-11-20</span>` for static renderings; a parse rule ignores that span so a
paste never turns it into note text. The share view's sanitiser drops `data-owner` (no email / user id
leaves), keeps the span. Shared text form (`formatTaskMeta`): `@Dana Lee, due 2026-11-20`.

**Markdown.** `- [ ] Send the deck (@Dana Lee, due 2026-11-20)`; parsed back from the end of the task's first
line (before a block marker comment). Names are backslash-escaped (`(`, `)`, `,` too) so they can't end the
suffix; task text that merely *looks* like a suffix gets its `(` escaped, so it stays text. Lossy (documented):
Markdown keeps only the owner's name, not email/user id. The suffix regex uses a look-behind (no quadratic
blank-run scan; markdown-it itself is quadratic on 50k-space lines, not us). Notion: the same text appended to
the `to_do`'s rich text.

**Editor UI (Designer).** React node view for task items (`ReactTaskItem`, used by `OatEditor`; the headless
schema is unchanged): checkbox · content · chips on the right. Owner chip = initials avatar (`--me` tint, the
"person" colour already used for mentions) + name; due chip = calendar icon + relative label (Today /
Tomorrow / weekday within a week / "Nov 20"), overdue tinted `--destructive`, due today `--warning`, done
items never look overdue. Empty items show quiet "Assign" / "Due" ghost buttons on row hover/focus (always
faintly visible on touch). Pickers are `@oat/ui` Popover + Command: people from `onTaskAssigneeQuery`
(→ `GET /api/tasks/assignees`: workspace members, me first, then the meeting's participants), or "Assign to
“typed name”"; due picker = Today / Tomorrow / Next week + native date input + Clear. Read-only editors show
chips as labels and a disabled checkbox. All values are tokens (no new colours).

**Enhance mapping (`@oat/ai` `enhance-tasks.ts`).** Owner: email → exact folded name (case/accents) → unique
first/last name or email local part → "Dana L."-style prefix; ambiguous or unknown → `{ name }` only.
People = workspace members (with user ids) + note-taker + attendees, merged by email. Due: ISO dates;
today/EOD; tomorrow; weekdays (next occurrence *after* the meeting day; "next Friday" = the same rule);
end of week/next week/end of month; "in N days/weeks"; "Nov 20"/"20 November" (rolls to next year if past) —
relative to the meeting's day in its time zone. Unparseable phrases stay in the text as `— due <phrase>`
(the pre-8.4 suffix minus the owner, which is now an attribute). `me` tasks keep the owner/due the user set
(carried on `NoteLine`, also kept in the re-enhance notes snapshot); the model can't change them. No prompt
change; eval unchanged (20/20, 9/9, 0 regressions).

**Owners → users (indexing).** A stored `owner.userId` is trusted only if that user is a member of the
document's workspace; else an `owner.email` matching a member gives the user id. "Assigned to me" = owner
user id, or (no user id) owner email = my email, at query time.

**API.** `GET /api/tasks?view=assigned|created|all&status=open|done|all&due=any|overdue|soon&today=&workspaceId=`
(permission rule in SQL — member of a live workspace, live doc, own or not private — then `canReadDocument`
per row; `canEdit` per item). `PATCH /api/tasks/:id { done, baseVersion }` rewrites `checked` on that block and
saves through `updateDocument` (same validation, version bump, 409 `stale_version` + server copy), then
re-extracts; viewers 403, unreadable 404; a block that left its note → 404 and the stale row is dropped.
`GET /api/tasks/assignees?documentId=&q=` needs read access to the note. "Created by me" = items in notes I own.

**/tasks page.** Tabs (Assigned to me / Created by me / All in workspace) + Status and Due selects, all in the
URL; groups by note (meeting icon, title link, date), newest first; rows: checkbox, text (→
`/d/<id>?block=<blockId>`), owner chip ("You"), due chip. Ticking is optimistic; on 409 it retries once on
the server's version, else reverts + toast + reload. Empty states per view/filter; skeleton while loading;
inline error with retry. Sidebar entry under Home, ⌘K "Go to" entry, breadcrumb from `sections`.
`?block=` (`BlockFocus`, mounted next to the document page) scrolls to the block and highlights it briefly.

**e2e.** `web-server.ts` now also runs the index worker in-process (own Redis prefix, 200 ms debounce,
embeddings from the in-process mock LLM), so e2e exercises the real change_log → worker path.

**Touched outside the listed areas (minimal, needed):** `apps/web/src/server/enhance/service.ts` (passes
workspace members to the task mapping, +12 lines), `apps/web/src/components/document/document-editor.tsx`
(one prop: `onTaskAssigneeQuery`), `apps/web/src/app/(app)/d/[docId]/page.tsx` (mounts `BlockFocus`),
`apps/web/src/proxy.ts` (`/tasks` protected), `apps/web/e2e/web-server.ts` (worker), `packages/indexing`
backfill (also syncs action items). Follow-ups for the orchestrator: log D-29; a line in DEV.md "Retrieval
indexing" that the worker also maintains `action_item`.

## Review
**Reviewer, 2026-11-14: `changes` (1 finding).** Read the task file and `git diff $(git merge-base main
task/8.4-action-items)..task/8.4-action-items`; viewed the evidence screenshots.

Checked and fine: `listActionItems` SQL rule (memberships only, live workspace + doc, own-or-not-private) matches
`canReadDocument` for live docs, plus the per-row re-check, so My tasks / All in workspace can't show others'
private notes, trashed notes or other workspaces. Toggle: 404 unreadable, 403 viewers (`assertCan
editDocument`), writes via `updateDocument` CAS on `baseVersion` (409 + server copy); an assignee who can't edit
can't toggle (UI disables with a tooltip; consistent with D-4). Assignees endpoint needs read access; member
emails are already visible to every member (workspace settings), no share-token path reaches it. Schema change
is additive (absent attrs valid; owner keys/lengths/email/day validated); share sanitiser drops `data-owner`
and keeps only `@Name, due …`; Markdown/Notion carry the name only. Worker: idempotent upsert per
(document, block), deletes vanished blocks, advisory lock + version guard, queue re-runs a job re-enqueued
while active; FK cascade on hard delete. Dates are zone-less days; meeting day taken in the meeting's zone;
"Friday" on a Friday = next week (documented).

1. **Partial owner matches resolve against every workspace member, not just the meeting's people** —
   `packages/ai/src/enhance-tasks.ts:99-114` (people built in `taskMappingFromContext`, `:310`). "Sam" in a
   meeting with an external/unlisted Sam resolves to the only workspace member called Sam (who wasn't there),
   storing their `userId`, so the task lands in a stranger's "Assigned to me" on any workspace-visible note. That
   is a guess, not a clear match. Fix: keep email and exact full-name matching against members + attendees, but
   run the partial rules (single first/last name, initial, email local part) only over the note-taker + meeting
   attendees (members merged in by email, so an attending member keeps their user id); add a test with a
   non-attending member whose first name matches.

Optional:
- `apps/web/src/server/tasks/service.ts:146`: if the write-through `syncActionItems` throws after the note was
  written, the client gets a 500 and reverts a tick that did save; catch + log (the worker catches up).
- `packages/ai/src/enhance-tasks.ts:267`: "this Friday" said on a Friday becomes next week's Friday; consider
  `this <weekday>` = today when it is that day. `monthDay` (`:212`) returns null for "Feb 29" in a non-leap
  year instead of trying next year.
- `packages/db/src/action-items.ts:217`: list silently caps at 500 rows; no "more" indicator in `/tasks`.
- `editor-chips.png`: owner chip on a task without a due date isn't right-aligned with rows that have one (the
  hidden "Due" ghost keeps its width).
- Stale guard (`action-items.ts:109`) can't protect a document with zero stored rows; harmless because the
  newer change re-runs the job, but worth a comment.

**Resolution (implementer, round 2; main @ 8d763f0 merged):**
1. Fixed. `resolveTaskOwner(raw, people, inMeeting)`: email and exact full name match everyone (members +
   attendees + note-taker); partial rules (one first/last name, "Dana L.", email local part) run only over
   `TaskMapping.inMeeting` = note-taker + this meeting's attendees, with members' user ids merged in by email.
   Tests: a non-attending member "Sam Park" vs attendee "Sam Rivera" → "Sam" = Sam Rivera; "Riley" with only an
   absent member Riley Stone → name only; attending member keeps user id; exact/email still reach any member.
Optional, all done: toggle write-through `syncActionItems` failures are caught + logged (the note saved; the
worker catches up); "this Friday" said on a Friday = that day ("Friday"/"next Friday" = next week); "Feb 29"
rolls to the next leap year; `/api/tasks` returns `truncated` (fetches 501, shows 500) and /tasks says
"Showing the first 500 tasks…"; empty "Assign"/"Due" ghosts render before the chips (`order: -1`) so set chips
stay right-aligned; version-guard comment explains the zero-rows case.
